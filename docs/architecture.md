# Architecture

## Overview

SafeClaw runs Claude Code inside a sandboxed Docker container, accessible via a web terminal. All authentication is handled via environment variables, making it easy to deploy locally or in the cloud.

Everything on the host is one Go binary, `safeclaw`. It talks to Docker by running the `docker` CLI with argument lists (never through a shell), so it works with any Docker-compatible CLI. The same binary is compiled into the image, where ttyd runs its hidden `safeclaw ttyd-wrapper` subcommand.

## Web terminal

The user interacts with Claude Code through a browser, not a local terminal. This gives full access to the native Claude Code UI rather than building a custom one on top of the Agent SDK.

- **ttyd** serves a web terminal over HTTP/WebSocket on port 7681 inside the container, published on `[::1]` at the first free port from 7681 up
- **tmux** manages the Claude Code session inside the container (session `main`)
- `safeclaw ttyd-wrapper` creates the tmux session and starts `claude --dangerously-skip-permissions` if it doesn't exist, then attaches
- One port, one ttyd process, one tmux session per container

Containers created from the upstream image don't contain the `safeclaw` binary, so `run` falls back to their `/home/sclaw/ttyd-wrapper.sh`.

### Umask

Some Docker versions start `docker exec` processes with a umask of `0000` instead of the container's, and safeclaw starts everything in a session with `docker exec`. So ttyd is started under `umask 022`, and `safeclaw ttyd-wrapper` sets it again before it runs tmux, which covers `run -q` starting the tmux session without ttyd. The tmux server, every shell in it, and Claude Code inherit it, so files they create, including in the history mount on the host, are not world-writable. `safeclaw attach` only runs a tmux client, so its shells come from the same server. The legacy tmux script and the git config script run under `umask 022` too, and the env file and the terminal credential are written under `umask 077`. A running session picks this up on its next `run`, which restarts ttyd and tmux.

### Attaching from the host

`safeclaw attach NAME` runs `docker exec -it --user sclaw safeclaw-NAME tmux attach -t main`, but not on the host terminal. The tmux server runs as `sclaw`, the same user as Claude Code and everything it starts, so code in the session can change any tmux option and make tmux send attached clients anything, such as an OSC 52 clipboard write from `tmux set-buffer -w` or a pane's sequence wrapped in tmux passthrough. So `attach` puts the host terminal in raw mode, runs docker on a pseudo-terminal of its own, copies keystrokes to it, resizes it when the host terminal is resized, and passes its output to the host terminal through a filter that drops:

- OSC sequences other than window titles (0, 1, 2), hyperlinks (8), and default and cursor colours (10, 11, 12, and the resets 104, 110, 111, 112), which drops OSC 52 clipboard writes and reads. An allowed OSC is dropped too when it is longer than 8 KiB or holds a control character
- the target of an OSC 8 hyperlink that isn't an http or https URL, or whose host is `localhost`, a name under `.localhost`, a loopback address, or `0.0.0.0` or `[::]`, on any port. The link is replaced by the sequence that ends one, so its text is still shown, as plain text. Numeric hosts are read the way browsers read them, so `127.1` and `0x7f000001` count as loopback, and a URI that isn't printable ASCII, or whose host isn't a plain DNS name or IP address, is refused too. This matches the dashboard terminal, which only opens http and https links off loopback: the host terminal hands a clicked link to the OS, which can open a `file://` target, such as a file the session wrote into a mounted directory, or another scheme in another app, and a loopback target can reach the dashboard, whose cookie is sent to its host on any port, or a session's web terminal. Every port is refused since `attach` doesn't know which port the dashboard runs on. Names that only resolve to a loopback address through DNS are not caught, since they don't get the dashboard's cookie
- DCS, SOS, PM, and APC strings, and screen and tmux title strings (`ESC k`), which drops tmux passthrough, terminal capability queries, and graphics and terminal-specific commands carried in them
- CSI `t` window operations other than the size reports and the title stack (14, 15, 16, 18, 19, 22, 23), so the session can't move, resize, or iconify the host window or read its title. A title stack pop with none of the session's own pushes left, and a push past 8, are dropped too, so the session can't pop the host's titles or push them off the stack. Kitty keyboard flag pushes and pops are kept balanced the same way
- CSI `i` media copy, which can send what follows to a printer
- C1 control bytes, raw or UTF-8 encoded, and text that isn't valid UTF-8, such as an overlong encoding of a C1 control, which some terminals decode anyway

Text, colours, cursor movement, the alternate screen, mouse and bracketed paste modes, and queries whose replies go back to the session pass through unchanged. `attach` pushes the host terminal's titles on its title stack (`CSI 22 t`) before it starts, and after it detaches, or the connection drops, it resets what the session left set and pops them (`CSI 23 t`). The filter tracks the modes it passes on, so only those left set are reset: synchronized output, mouse reporting and its encodings, focus events, bracketed paste, application cursor keys and keypad, xterm modifyOtherKeys, kitty keyboard flags, the alternate screen, a hidden cursor, and local echo. A clean tmux detach resets them itself, so then only the titles are restored. Terminals without a title stack ignore the push and pop. The session can't set the host clipboard, so tmux copy mode only copies into tmux's own buffers. The dashboard's session info dialog gives the `safeclaw attach NAME` command for the same reason, rather than the raw `docker exec`, which would connect the host terminal to tmux directly.

`safeclaw build`, `safeclaw pull`, and `safeclaw auth login` pass docker's output through the same filter, since it comes from the image: a build's `RUN` steps, or `claude setup-token` in the sign-in container. When stdout and stderr are both terminals, docker runs with them on a pseudo-terminal of its own, which is its controlling terminal, so its progress display still works and `docker exec -it` still gets the terminal's size, while stdin stays on the host terminal, so docker reads it and sets its mode itself, as it would without safeclaw. The titles and modes are restored afterwards as for `attach`. Otherwise docker's stdout and stderr are each filtered on the way.

`safeclaw ttyd-wrapper` also starts the tmux server with `set-clipboard off` and `allow-passthrough off`, so programs that leave those options alone don't send clipboard writes or passthrough to any client, including the web terminal. That is not the control: code in the session can turn both back on.

### Terminal credential

The published port is not private to the session's owner: other session containers can reach it through the runtime's host gateway, and directly wherever two sessions share a network that doesn't block traffic between them (see [session network](#session-network)), and so can any local process or a browser page allowed to open a WebSocket to loopback. So ttyd requires a credential and runs with `-O`:

- ttyd requires a per-session credential, user `safeclaw` and a password made with `crypto/rand`. It is kept in `~/.config/safeclaw/ttyd/NAME` (honoring `XDG_CONFIG_HOME`), a 0600 file in a 0700 directory, outside the history directory that is mounted into the container, where `safeclaw url` and the dashboard's relay read it. It is never followed through a symlink and is removed with `safeclaw rm`. Every time `run` or the dashboard starts ttyd, it gets a new one, which is written to the host file and the container's credential file before ttyd starts: for a new container, including a recreate and a run after `safeclaw build --recreate`, for a stopped container started again, and for a running one whose ttyd is restarted. The old container's processes could read the credential from its file in the container, and a recreate can give the session wider secrets, so the old credential must not open the new terminal. A stopped container's published port is released, and another local user can bind it and answer an open tab's reconnect or reload, to which the browser sends its cached credential for that origin without asking, so a credential from before the stop must not open the terminal once it is started again. It is replaced only when ttyd is about to start, so no running ttyd still takes the old one, and a container restored after a failed recreate runs no ttyd until the next `run` starts one with a new credential. Nothing is rotated on stop: a stopped session runs no ttyd, and every way back starts it with a new credential. An open tab therefore needs the new URL after a `run`, which prints it, or the dashboard's terminal, which always relays with the current one
- The credential is on no command line, ttyd's included: on a native Linux docker host, container processes are host processes, and any local user can read their command lines from `ps` or `/proc/PID/cmdline`. It is written to `/home/sclaw/.ttyd-credential` in the container on stdin, a 0600 file sclaw owns, and ttyd reads it with `--credential-file`, which the image's ttyd gets from `setup/ttyd/credential-file.patch`; the patch also stops ttyd logging the encoded credential at startup, reads the file without a stdio buffer, and clears its copies of the credential with `explicit_bzero`. It refuses a credential over 180 characters, whose base64 form would not fit the 256 byte buffer ttyd builds its `/token` response in, and so would abort ttyd on its first `/token` request; safeclaw's credentials are about 50. A file is used rather than an environment variable because `/proc/PID/environ` is readable by the same user as the file, and the file keeps the credential out of the environment every process in the terminal inherits. The image carries the label `io.github.josegonzalez.safeclaw.ttyd-credential-file`. An older image's ttyd, or upstream's, takes the credential only with `-c`, on its command line, so `run` and the dashboard's start refuse to create a session from an image without the label, or recreate one from it, and say to update it with `safeclaw pull` or `safeclaw build`; every image published up to v0.2.0 lacks it. A session whose container lacks the label, made by an earlier version from such an image, is recreated from the image once the image has it, keeping its port, variant, secrets, IPC and auto memory choices, mounts, and history like any other recreate, and refused until then, before anything is stopped or changed. Like other recreates, it is refused while the session is [offline](#offline-sessions)
- `-O` refuses WebSocket clients whose `Origin` doesn't match the `Host` they connected to

ttyd checks the credential twice: as basic auth on every HTTP request and the WebSocket upgrade, and as the `AuthToken` in the WebSocket's first message, which its own page fetches from `/token`.

Once a browser has opened the URL with the credential, it keeps sending that credential to the session's port, and the page it gets passes `-O` because the page's own origin is the session's. Any other page on loopback, such as another session that replaced its own ttyd, could otherwise frame it invisibly and pass the user's keystrokes through to the session. So the image's ttyd is built from source with `setup/ttyd/refuse-framing.patch`, which makes every response it sends headers for, the index page, `/token`, the base-path redirect, the 401 and the 404 alike, carry `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`. The browser then refuses to render the terminal inside a frame on any page, without relying on the page's script. ttyd answered 404 with libwebsockets' `lws_return_http_status`, which can't add headers, so the patch sends its own. The error pages libwebsockets sends itself, for a malformed request before ttyd sees it, still lack the headers, since adding them would mean patching libwebsockets, and they carry no terminal to frame. The patch needs no flag, so the same ttyd arguments work with older images, whose ttyd lacks it until the image is updated and the session recreated. Nothing needs to frame ttyd: the dashboard's frames show its own terminal page and relay the WebSocket, see [dashboard access](#dashboard-access).

`safeclaw run` prints the session URL with the credential in it, `http://safeclaw:PASSWORD@[::1]:PORT`, so the browser logs in to ttyd directly, and `safeclaw url NAME` prints it again for a running, online session without touching it. `safeclaw ls` shows the URL without it.

Opening a browser hands the URL to `open` or `xdg-open`, whose command line other local users can read, and the browser keeps it in its history. So `run` and `safeclaw url NAME --open` first look for a running dashboard: for each token file in `~/.config/safeclaw/dashboard/` (the default port first, read without following symlinks), they send `http://127.0.0.1:PORT/dashboard-proof` a random nonce, never the token, with a one second timeout and no proxy, and check that the answer is HMAC-SHA256 of the port and nonce keyed by the file's token. The first dashboard that proves it holds its file's token has its terminal page, `http://127.0.0.1:PORT/sessions/NAME/terminal`, opened, which carries no credential and needs the dashboard's own login, so a browser that isn't logged in gets the dashboard's 401 page. A file left by a dashboard that has exited fails the proof, even when another local user took over its port, and is skipped and removed. See [finding the dashboard](dashboard.md#finding-the-dashboard). With no dashboard answering, they open the URL without the credential, such as `http://[::1]:PORT`, which ttyd answers with a basic auth prompt, and say to log in as `safeclaw` with the password in the printed URL, so the credential never reaches the opener. `safeclaw url` also prints the warnings `run` gives about a session an earlier version created that is still published on `127.0.0.1` or whose ttyd takes its credential on its command line, on stderr, saying whether to update the image before `run` recreates it. `run` doesn't open an offline session's terminal, which is unreachable. The dashboard never sends the browser to the session's port; it proxies the terminal instead, see [dashboard access](#dashboard-access).

Sessions are published on `[::1]` rather than `127.0.0.1` because `127.0.0.1` is where the dashboard's cookie is set, and cookies aren't scoped by port. Code in a session runs as the same user as its ttyd, so it can replace ttyd with any server on that port; if the browser were ever sent to `http://127.0.0.1:PORT`, that server would get the dashboard's cookie. With the port on `[::1]`, nothing a session controls listens on `127.0.0.1`. Session URLs name `[::1]` too, rather than `localhost`: a browser sends a page on `localhost` every cookie other local web apps set for `localhost`, and may connect to `127.0.0.1` for it, where nothing holds the session's port and another local user could listen. The image's ttyd is also built with `setup/ttyd/bracketed-ipv6-origin.patch`, because upstream ttyd's origin check strips the brackets from `Origin` but not from `Host`, so it never passes for `[::1]:PORT`. The image carries the label `io.github.josegonzalez.safeclaw.ttyd-bracketed-host`. No session URL names `localhost`, which a browser falls back to `127.0.0.1:PORT` for when `[::1]:PORT` refuses, as it does while the session is stopped and its port released, and an open tab's reconnect then sends its cached credential to whatever another local user bound there. Publishing older sessions on `127.0.0.1` as well would hand them the dashboard's cookie instead. So `run` and the dashboard's start refuse to create a session, or recreate one, from an image without the label, and say to update it with `safeclaw pull` or `safeclaw build`; every image published up to v0.2.0 lacks it. A session on `[::1]` whose container lacks the label, made by an earlier version from such an image, is recreated from the image once the image has it, like any other recreate below, and refused until then. While such a session still runs, `safeclaw url` refuses to print its URL, `safeclaw ls` shows none, and the dashboard's terminal still reaches it through the relay, which no browser connects through. Sessions created before terminals moved to `[::1]` are still published on `127.0.0.1` or every address, so `run` and the dashboard's start recreate them on `[::1]`, keeping their port, variant, secrets, IPC and auto memory choices, mounts, and history like any other recreate. That is only done when the session's image has the label, since older ttyd refuses the `[::1]` URLs a recreated session gets. Until then the session is refused, since its image's ttyd also lacks `--credential-file` and would take its credential on its command line, and `run` says to update the image with `safeclaw pull` or `safeclaw build` and run it again. Like other recreates, it is refused while the session is [offline](#offline-sessions).

## Dashboard access

The dashboard listens on `127.0.0.1`, and holds `[::1]` on the same port too so no other local user can take the `[::1]` side of `localhost:PORT`, but that only keeps other machines out: code inside a session container can reach host loopback through the runtime's host gateway on some runtimes (observed on OrbStack via `host.docker.internal`), and any local process can connect too. Every route therefore needs a token that `safeclaw dashboard` makes with `crypto/rand` each time it starts:

- The printed URL, `http://127.0.0.1:PORT/?token=...`, swaps the token for an HttpOnly, SameSite=Strict cookie named `safeclaw_dashboard_PORT` and redirects to the same URL without it, so the token leaves the address bar and history. The cookie holds a separate random value that the dashboard keeps in memory, not the token, so it only works as that cookie and only until the dashboard stops or the login ends (see [logins and logout](#logins-and-logout)). The redirect's fragment carries a second random value, the login's secret, which must come with the cookie (see [the second secret](#the-second-secret))
- API clients send `Authorization: Bearer TOKEN`, reading the token from `~/.config/safeclaw/dashboard/PORT.token` (honoring `XDG_CONFIG_HOME`). The directory is 0700 and the file 0600; it is replaced on start and removed on exit, including on SIGHUP
- Anything else, static files included, gets 401 before any session or docker call. Tokens, cookies, and secrets are compared in constant time

The cookie is only ever set for `127.0.0.1`, and the token URL on `localhost` first redirects there. Any other `Host`, `::1` included, is refused. Cookies aren't scoped by port, and session terminals are served from inside their containers at `[::1]:PORT`, so no name a session can serve on gets the cookie. Restarting the dashboard makes a new token, so open the newly printed URL again.

The dashboard shows each session's terminal through itself rather than framing ttyd:

- `GET /sessions/NAME/terminal` is the dashboard's own page: vendored xterm.js and the client in `static/app.js`, with a `Content-Security-Policy` allowing only the dashboard's own scripts and connections. The iframe and the `open` link point at it
- Its WebSocket, `GET /sessions/NAME/terminal/ws`, is behind the token like every route, takes the cookie with a one-use ticket in place of the secret, since a browser can't add headers to a WebSocket, and only accepts an `Origin` equal to the dashboard's own, since other pages on `127.0.0.1` are the same site and get the SameSite cookie. The dashboard opens a new WebSocket to the session's published port, so the browser's cookie and `Authorization` header never reach it, and adds ttyd's credential as basic auth and as the first message's `AuthToken`, sending `localhost:PORT` as the `Host` and `Origin` so `-O` passes for patched and older ttyd alike. These headers never come from or reach a browser, so they carry no cookies. Then it relays messages both ways

Nothing the session's port returns is ever served as a page: only the terminal bytes on the WebSocket come from ttyd, and xterm.js renders them as text. A session that replaced its ttyd therefore can't run script on the dashboard's origin, which would have the dashboard's full authority. Terminal links open in a new tab, except links to localhost, names under `.localhost`, and loopback or unspecified addresses, on any port, as `safeclaw attach` refuses them. The main page's own policy refuses inline script too, see [dashboard security](dashboard.md#security).

The `Host` check (against DNS rebinding) and `http.CrossOriginProtection` (against other websites driving the dashboard from your browser) still apply on top of the token.

### The second secret

Cookies aren't scoped by port, and every port on `127.0.0.1` is the same site, so the browser sends the cookie to anything else listening there once the user opens a page on it, even through a cross-site link: a session still published on `127.0.0.1` from before sessions moved to `[::1]`, or a server another local user runs. Whoever gets it can replay it from a client that sends no `Origin` or `Sec-Fetch-Site`, which `http.CrossOriginProtection` lets through, and that client can make up any header and fetch any page the cookie opens. So the cookie alone opens only what holds no state, and everything else needs a value it can't reach:

- The token exchange redirects to `PATH#safeclaw-secret=SECRET`. The secret is a random value the dashboard keeps in memory, like the cookie's. The browser never sends a fragment to a server or puts it in a `Referer`, and `app.js` stores it in `localStorage` and removes it from the address bar with `history.replaceState` before htmx starts, so it isn't left in history or in htmx's `HX-Current-URL`
- `localStorage` is scoped to the origin, port included, so only the dashboard's own pages can read it. Every tab of the dashboard has it, including tabs `safeclaw run` and typed URLs open. Each login overwrites it, and logging out removes it. It stays in the browser profile after the dashboard stops or the login expires, but it is worthless then, since the dashboard no longer accepts it, and only processes running as the user, which can read the token file anyway, can read the profile
- `app.js` sends it in the `Safeclaw-Secret` header on every htmx request, the SSE stream included, which the htmx 4 extension opens with `fetch`. It is never put in a URL
- The cookie alone opens only the page shells, `GET /` and `GET /sessions/NAME/terminal`, and static files, which are the dashboard's own code and show no session or host state. The sessions table, frames, banner, and the new session form's variant and secret pickers are fragments the page fetches with the secret. Every other route, the JSON API included, needs the cookie with the secret, or the bearer token
- The terminal WebSocket can't carry a header, so the terminal page first asks `POST /tickets` (with the secret) for a ticket for its WebSocket path and opens the socket with it in the `ticket` query parameter. A ticket is random, works only with the cookie, only for that path, only once, and only for 30 seconds, and at most 64 are outstanding
- A page without the secret, or whose secret the dashboard refuses, sends no requests, clears what it showed, and says to open the printed URL. A login in another tab reloads it, and a logout in another tab clears it

No route returns the secret, so a listener that captured the cookie gets the page shells and nothing else. A bearer header decides on its own, so API clients are unaffected.

### Logins and logout

Each token exchange is a login of its own, with its own cookie value and secret, so one browser logging out or expiring leaves other browsers and profiles logged in. A browser has one login per dashboard, since its cookie is named after the port: opening the printed URL again ends the login whose cookie it sent and starts a new one. Logins are bounded in time, so a captured cookie and secret stop working even while the dashboard runs:

- A login ends 7 days after it started, which is also the cookie's `Max-Age`, however much it is used
- A login with no request in flight for 12 hours ends too. A request in flight, such as an open tab's SSE stream, keeps it, so an open dashboard tab stays logged in until the 7 days are up, while one closed overnight is logged out
- At most 32 logins are kept; another login ends the least recently used one
- The `log out` button posts `POST /logout` with the secret, which ends the login: its cookie value, secret, and outstanding tickets stop working, and its requests in flight, SSE streams and terminal WebSockets included, are closed. The response clears the cookie, and the page removes the secret from `localStorage`, takes down the table and frames, and shows the "Not logged in" notice, as do the dashboard's other tabs in that browser. Logging out needs the cookie with the secret, which a form on another site can't send, and `http.CrossOriginProtection` applies too. The bearer token has no login to end, so it gets 400
- Tickets belong to the login that asked for them, and only that login's cookie can use one. A ticket minted with the bearer token works with any login's cookie

The dashboard keeps logins in memory under the SHA-256 of their cookie value, so finding one never compares the value itself in variable time. The secret is compared in constant time.

To log in again after a logout or expiry, open the URL `safeclaw dashboard` printed, or `http://127.0.0.1:PORT/?token=` followed by the token in `~/.config/safeclaw/dashboard/PORT.token`.

Anything else listening on `127.0.0.1` can still set a cookie named `safeclaw_dashboard_PORT`, since cookies aren't scoped by port. One set for the same path replaces the real cookie and logs that browser out, which the page shows as "Not logged in"; that only ends the one browser's access until it logs in again, and the stale login ends when it idles out. It can't log in that browser as anyone else, since the dashboard only accepts cookie values it made. A cookie set for a narrower path, which the browser sends first, doesn't hide the real one, since every cookie with the dashboard's name is tried.

## Session lifecycle

### Session names

Session names are lowercase letters, numbers, `.`, `_`, and `-`, starting with a letter or number, and may not start with `safeclaw-`. Each session is the container `safeclaw-NAME`, the history directory `~/.config/safeclaw/sessions/NAME`, and the state files named after it, so one name never reaches another session's container with different history or state, including on a case-insensitive filesystem. Commands also accept the container name, with its one `safeclaw-` prefix removed, and the CLI lowercases names like the dashboard's create dialog does, so `Work` is the session `work`. The API and the dashboard's session routes refuse names that aren't already lowercase. Create, in the dialog and `/api/create`, lowercases and removes the prefix before checking whether the name is taken, so `safeclaw-work` is refused as in use whenever `work` is, and a name still starting with `safeclaw-` after that, like `safeclaw-safeclaw-work`, is refused as invalid.

A new session or sandbox name can be at most 230 characters, so every file named after it on the host fits the usual 255-byte limit on a file name. The longest is a session's history directory moved aside by `--fresh-history`, `NAME.old-YYYYMMDDTHHMMSS+0000`, 25 characters longer than the name; a saved network state's temporary file, `.NAME.RANDOM.tmp`, and a sandbox's cp-in lock, `safeclaw-NAME.lock`, are shorter. Docker sets no shorter limit on container names. `run`, `new`, `sandbox run`, `sandbox exec --ephemeral`, and the dashboard's create dialog and `/api/create` refuse a longer name, naming the limit, before any container is created. Only creating checks it, since a container made with a longer name by an earlier version can't be told apart from a new one by its name: such a container can still be started, stopped, removed, and inspected, but `run` and `sandbox run` refuse to recreate it under that name, so `rm` and a shorter name are the way forward.

Earlier versions accepted uppercase letters. While a container made that way matches a session's container case-insensitively but not exactly, such as `safeclaw-Work` for `work`, the session is refused: the CLI refuses `work`, `Work`, and `WORK` alike instead of acting on either container; `run`, `new`, and the dashboard's start and create refuse to create or start `work`; and the dashboard's stop, delete, offline, online, and terminal, and their API routes, refuse `work` with 409, since on a case-insensitive filesystem the two would share the history directory, ttyd credential, and network state. The error names `docker rm -f safeclaw-Work` to remove the old container. `safeclaw rm` would remove the state `work` shares with it, and renaming it with `docker rename` would keep it mounting the shared history directory, so removing it is the only fix. Its history stays on the host, and `work` can then be created and uses it. Run and start check under the session's own lock, which is named after the lowercase name, so the check can't race another run of the session, and no run can make a mixed-case container since those names are refused.

### Creating, starting, and refreshing

`safeclaw run` (and the dashboard's create and start) all go through the same code path:

1. Pick the [image variant](#image-variants) and check its image exists and carries no [safeclaw labels](#labels) of its own, pick the [secrets](#choosing-secrets) the session receives (from the flags, the container's labels, or the [kept choices](#kept-choices) of a session without a container), then check that the Claude token is present if the session receives it (prompting for it only in `run`) and that every listed secret exists
2. Reuse the container's existing port, or pick the lowest port no `safeclaw-*` container reserves and nothing on the host is listening on, on `[::1]` or `127.0.0.1`
3. Create, start, or refresh the container. With `-v`, a `--variant` other than the container's, a different set of secrets, a different [`--host-ipc`](#ipc-namespace) or [`--no-memory`](#auto-memory) choice, or [`--fresh-history`](#reused-history), or a terminal still [published on `127.0.0.1`](#terminal-credential) when the image's ttyd accepts `[::1]` URLs, or a ttyd that [takes its credential on its command line](#terminal-credential) when the image's reads it from a file, an existing container is recreated, keeping its port and whichever of its mount, variant, secrets, IPC, and auto memory choices were not given again. Every volume is checked before the old container is removed, and if the new one can't be created, the old one is created again with its port, mounts, variant, secrets, IPC, and auto memory choices, so a failed recreate never loses the session's secret set. A running container has ttyd and tmux restarted so new env vars take effect: its ttyd is stopped with SIGTERM, then SIGKILL if it is still there after 5 seconds, and the run fails, before the credential is rotated, if pkill fails or a ttyd process or anything listening on its port is still there 5 seconds after that, so an old ttyd never keeps taking the old credential while the host file and the printed URL carry a new one. An [offline](#offline-sessions) session is never recreated, and starting it keeps it offline
4. Write the env file, `/etc/safeclaw/env`, from the secrets the session receives
5. Configure git from the GitHub account if the session receives `GH_TOKEN`
6. Keep the session's secrets and auto memory choices on the host as its [kept choices](#kept-choices), then write the auto memory choice to its managed settings file, before Claude Code starts
7. Start ttyd with a new [terminal credential](#terminal-credential), and wait up to 10 seconds for it to answer a request carrying that credential, made inside the container by curl reading it on stdin. A refusal means another ttyd holds the port and fails the run right away, as does no answer by then. With `-q`, wait for Claude Code's input prompt before sending the query, typed literally with `tmux send-keys -l --` so a query starting with `-` isn't read as options

Runs of one session are serialized across safeclaw processes, such as `run` and the dashboard, by a lock file for each session in `~/.config/safeclaw/ttyd/.ensure/`, held for the whole run, so two runs can't each rotate the credential and leave the host file holding one while ttyd took the other. A run waiting on it gives up when its context ends, such as on Ctrl-C, and runs of other sessions don't wait for it. Locks are taken in one order: the session's lock, then the lock that serializes port allocation within a process, then the [network lock](#offline-sessions), which a run releases once the container is created or started. `rm`, `net off`, and `net on` take only the network lock, and nothing takes the session's lock while holding another, so they can't deadlock.

### Labels

safeclaw records what it decided about a container in `safeclaw.*` labels: its type (`safeclaw.type`), [variant](#image-variants), the image tag it was created by (`safeclaw.image`), [secrets](#choosing-secrets), [IPC namespace](#ipc-namespace), [auto memory](#auto-memory), and whether it is a [sign-in container](#claude-code) (`safeclaw.auth`). Docker copies an image's labels onto every container made from it, so before creating a session, sandbox, or sign-in container, and before reusing a session or sandbox, safeclaw refuses an image that carries any `safeclaw.*` label other than the `safeclaw.variant` label naming its own variant. The error names the label, and the image has to be rebuilt without it. Every `safeclaw.*` label on a container safeclaw creates is then one safeclaw wrote, so an image can't make a session look like a sandbox, change its secrets, IPC, or auto memory choice, or get it removed as a stale sign-in container. Every session is labeled `safeclaw.type=session` and every sandbox `safeclaw.type=sandbox`; containers without the label, created by versions that left it off sessions, are interactive sessions. `run` and the dashboard's start refuse a container whose type is anything but `session`, before checking its image or changing anything, and the `sandbox` commands refuse anything but `sandbox`.

The image is checked by its tag, but a pull or build can move the tag to another image between the check and `docker run`, which would then create the container from an image that was never checked, with whatever labels it carries. So sessions, sandboxes, one-off sandboxes, and sign-in containers are run from the image ID (`sha256:...`) the check inspected, never the tag, and the choices made from the image's labels, such as whether its ttyd accepts `[::1]` URLs or reads its [credential](#terminal-credential) from a file, hold for the container that is created. A restored container after a failed recreate is checked and run by ID the same way. Docker then records only the ID as the container's image, so the tag it was checked by is kept in the `safeclaw.image` label, which `sandbox inspect` reports as `image`. `safeclaw build` and `pull` still find stale containers by comparing each container's image ID with the ID its variant's tag has now.

### Kept choices

Labels go away with the container, but the session's history directory does not, so a session's secrets and auto memory choices are also kept on the host, in `~/.config/safeclaw/choices/NAME.json` (honoring `XDG_CONFIG_HOME`), a 0600 file in a 0700 directory, outside the history directory that is mounted into the container, so the agent can't change them. They are written on every `run` and dashboard start once the container is in place, and from the container's labels just before `safeclaw rm`, `safeclaw build --recreate`, the dashboard's delete, or a recreate removes it, so sessions created before choices were kept get a record too. A session created with no container uses them for any choice its flags don't give, so after its container is removed, a plain `safeclaw run -s NAME` or a dashboard start creates it again with the same secrets and with auto memory still off. The file is read without following a symlink, and one that can't be read or names an invalid secret fails the run rather than dropping a choice. The file is named after the canonical session name, like the history directory. Sandboxes keep none, and neither does a mixed-case container left by an earlier version, so its record never replaces the lowercase session's on a case-insensitive filesystem.

Nothing removes the record: `safeclaw rm` and `--fresh-history` keep it, so the choices stay with the session name. To reset them, give them again, for example `safeclaw run -s NAME --all-secrets --no-memory=false`, which records the defaults. The [IPC namespace](#ipc-namespace) choice is not kept, so a session that shared the host's goes back to a private one when its container is removed.

### IPC namespace

A session gets docker's default private IPC namespace and its own `/dev/shm`, so code Claude Code runs can't see or attach to the docker host's shared memory, semaphores, or message queues. On a native Linux docker host that is the real host's; on Docker Desktop or OrbStack it is the Linux VM's. No `--shm-size` is set: Playwright starts Chromium with `--disable-dev-shm-usage`, so the browser works with docker's default 64 MB `/dev/shm`.

`--host-ipc` on `run` or `new` opts a session into `--ipc=host`, recorded in the `safeclaw.ipc=host` label so recreates keep it, and `--host-ipc=false` moves it back to a private namespace. Sessions created before private namespaces became the default share the host's without the label: `run` keeps them as they are with a warning, `--host-ipc=false` or `--host-ipc` recreates them with that choice, and any other recreate gives them a private namespace.

### Auto memory

Claude Code's auto memory lives in the session's [history directory](#reused-history), so what one conversation writes to `MEMORY.md` is loaded into every later one, including after the container is recreated. It stays on by default. `--no-memory` on `run` or `new` turns it off for a session, recorded in the `safeclaw.memory=off` label so recreates keep it, and in the session's [kept choices](#kept-choices) so it outlives the container, and `--no-memory=false` turns it back on. Changing the choice recreates the container, like `--host-ipc`. A session created over existing history with no kept choices, such as one whose container was removed before choices were kept, and no `--no-memory` flag gets auto memory on, with a warning that Claude Code loads the `MEMORY.md` the history holds.

The choice is set through Claude Code's managed settings, which take precedence over every other settings file, the `--settings` flag, and the environment, so the agent can't turn it back on. The image creates `/etc/claude-code/managed-settings.d/safeclaw-session.json` root:root 0644 with `{}` (from `setup/safeclaw-session.json`), and on every run, before Claude Code starts, safeclaw rewrites its contents as root, like the env file. With auto memory off it holds `autoMemoryEnabled: false` and sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in its `env`, since that variable set to `0` in the environment would otherwise turn auto memory back on; managed `env` wins over the environment. With auto memory on it holds `{}` again, leaving Claude Code's default. In containers from images without the file, root creates it to turn auto memory off, which needs no capability since root owns `/etc`, and leaves it absent otherwise. If it can't be written, the run fails before ttyd starts. Memory already in the history directory is kept but neither loaded nor written while auto memory is off; use [`--fresh-history`](#reused-history) to move it aside.

### Privileges

Sessions run with `--cap-drop ALL` and `--security-opt no-new-privileges`, like sandboxes, and with `--user sclaw`, rather than as whatever user the image's last `USER` line names, so a variant or image that ends as root still runs its session as sclaw. Every `docker exec` safeclaw runs in a session or sign-in container names its user too: `--user sclaw` for everything but the root writes below, which pass `--user root`, so none takes the container's default user. Everything in a session, apart from the env file, git identity, and auto memory setting writes below, runs as the unprivileged `sclaw` user, which needs no capabilities: Claude Code, git, gh, tmux, and ttyd don't, Playwright starts Chromium with `--no-sandbox` so it needs no user namespaces, and the terminal credential write is a file sclaw owns. The image has no sudo, and with `no-new-privileges` the setuid and setgid binaries it does have (`su`, `passwd`, `mount`, `ssh-agent`, and the like) run without gaining privileges, so even a `root` process started with `docker exec -u root` has no capabilities. safeclaw writes the env file, git identity, and auto memory setting that way, as root from the host, which works because root owns those files: without `CAP_CHOWN`, `CAP_FOWNER` or `CAP_DAC_OVERRIDE` it can write and create files it owns but can't chown them, so the image creates the env file with its owner and mode and safeclaw only rewrites its contents.

The history directory is mounted with plain bind-mount options: docker's `-v` and `--mount type=bind` take no `nosuid` or `nodev`, and a bind volume made with the `local` driver's `o=bind,nosuid,nodev` doesn't carry the flags into the container. The same protections come from the flags above: setuid bits are ignored under `no-new-privileges`, and nothing can make a device node without `CAP_MKNOD`.

Sessions created before this keep docker's default capabilities. `run` keeps them as they are with a warning, and any recreate, for example with `-v` or after `safeclaw rm`, drops them.

### Session network

Sessions are created on `safeclaw`, a bridge network safeclaw creates the first time it creates a session, with `com.docker.network.bridge.enable_icc=false` and the label `safeclaw.network=sessions`. Docker's default bridge lets its containers reach each other, so any unauthenticated service one session runs, such as a dev server, would be reachable from every other session there. With traffic between its containers off, sessions on `safeclaw` can't connect to each other, while each still reaches the internet and the host, and its ttyd is still published on `[::1]`. Docker's DNS on the network still resolves other sessions' container names, but connections to them are dropped. One shared network is used rather than one per session, since each network takes a subnet from docker's address pools, which a few dozen networks use up, and a shared one needs no cleanup: `rm` leaves it, and `docker network rm safeclaw` removes it once no session uses it.

The isolation comes from docker's firewall rules, so it holds on native Linux and Docker Desktop, but not where those rules are bypassed or off. OrbStack creates the network with the option but lets traffic between its containers through, as it does between separate networks, and docker run with `"iptables": false` installs no rules. On those, sessions can still reach each other's services. On every runtime, a session can also reach another's published ttyd through the runtime's host gateway, which is why ttyd needs a [credential](#terminal-credential).

A `safeclaw` network without the label or `enable_icc=false`, with another driver, or internal wasn't made by safeclaw for sessions, so `run`, the dashboard's start, and `net on` refuse to put a session on it, saying to remove it with `docker network rm safeclaw` so safeclaw creates it again. A recreate checks the network before it removes the old container. If the network was removed while no running container used it, for example by `docker network prune` with every session stopped, it is created again: a stopped session is reattached to the new network before it starts, since docker keeps the removed network's ID on the container and refuses to start it otherwise, and `net on` creates it before reconnecting an offline session.

Sessions created before sessions moved to `safeclaw` stay on the default bridge, and `run` warns about it. They move on their next recreate, for example with `-v`, `--variant`, `safeclaw rm` then `run`, or `safeclaw build --recreate`. An offline session that was on the default bridge goes back to it with `net on`, since its saved networks name it.

### Config directory

Before any command runs, safeclaw checks `~/.config/safeclaw` (honoring `XDG_CONFIG_HOME`, and following a symlink to its target). One owned by another user is refused, since they could read or replace the history, credentials, and tokens kept there; the error suggests removing it or setting `XDG_CONFIG_HOME`. One owned by the user but open to others, for example one made with `mkdir -p` to write `config.yaml`, is restricted to 0700 with a note. Directories safeclaw creates there are 0700, including `sessions/` and each session's history directory, and ones created open to others by earlier versions are restricted when a container is created for them.

### Volume mounts

`-v` (and the `volume` of the dashboard's create and `/api/create`) is a docker `host:container[:options]` spec. A leading `~` or `./` in the host path is expanded, and a host path that is still not absolute is a named volume, which is passed on unchecked. The host path is then checked with symlinks resolved: docker creates a missing one, so only its longest existing prefix is resolved, and a broken symlink is refused, since what docker would create through it can't be checked. It is compared with the [config directory](#config-directory), resolved the same way, by name and, where both exist, by file identity, so another spelling on a case-insensitive filesystem or another bind mount of the same directory counts as the same directory.

A host path that is the config directory, one of its ancestors such as `~`, `~/.config`, or `/`, or a path inside it is refused. The directory holds every session's terminal credential, the dashboard's API token, and the secrets kept in files when there is no keychain. With them, the session could open every other session's terminal, which may receive other secrets, and drive the dashboard, which can create a session with any mount, so even a read-only mount would let it out of its container. There is no flag to allow it: nothing a session does needs the config directory, and a project anywhere else, including under `~`, can be mounted by its own path. `run` refuses it before anything is locked, checked, or changed, and the dashboard's create refuses it with 422 in the dialog and `/api/create` with 400, before the session is created. A session whose container already has such a mount, made before they were refused, keeps running, with a warning on every `run`, and any recreate that would keep the mount is refused before the container is removed, naming `-v` with another host path, which replaces it, and `safeclaw rm`. Sandboxes refuse these mounts too, since their files reach the host through `cp-out`.

A host path that is, or contains, a docker or container runtime socket is mounted with a warning, rather than refused, since giving a session docker on purpose, for example by mounting `/var/run/docker.sock` to build images, is a setup some users choose. The socket gives the session control of docker and so of the host. The sockets looked for are the one `DOCKER_HOST` names when it is a `unix://` path, `/var/run/docker.sock`, `/run/docker.sock`, containerd's, podman's, and CRI-O's under `/run`, Docker Desktop's, OrbStack's, Colima's, and Rancher Desktop's under the home directory, and rootless docker's and podman's under `XDG_RUNTIME_DIR`, each one that exists, by the path it was found at and with symlinks resolved. `run` prints the warning, `/api/create` returns it in `warnings`, and the dashboard's create keeps the dialog open with it and a link to the new session's terminal, instead of closing and opening the tab on its own. Sandboxes print it too.

Two risks of a mount are left to the user, and documented next to the `-v` examples in the README:

- A read-write project mount lets the agent change anything in the project, including `.git/config` and `.git/hooks`. Git on the host reads that config and runs those hooks when it next runs in the directory there, so the agent can make git on the host run a command, through `core.fsmonitor`, `core.hooksPath`, `core.sshCommand`, an alias, or a hook such as `pre-commit`, as the host user, outside the container. Check them before running git on the host in a directory a session could write, or mount the project `:ro`.
- The `z` and `Z` options make docker relabel the host path for SELinux on hosts that enforce it, and the new label stays after the container is gone: `z` gives it a label every container can share, and `Z` one only this container can use, so other containers and host services confined by SELinux can lose access to it. Relabeling a directory such as the home directory or a system path can break the host. Sessions pass them on, since docker only relabels plain `-v` mounts; [sandboxes](#sandboxes) refuse them, since their mounts can't be plain `-v` ones.

## Sandboxes

`safeclaw sandbox run -s NAME` creates a headless container for opening untrusted files with `docker exec`, for example extracting text from PDFs, archives, or emails that have not been checked. It shares the `safeclaw-NAME` namespace with interactive sessions and is marked with the `safeclaw.type=sandbox` label, where interactive sessions get `safeclaw.type=session` (see [labels](#labels)).

A sandbox is created with none of what an interactive session gets: no secrets are written and no Claude token is needed, there is no git configuration, no ttyd, tmux, or Claude Code, no published port, no option to share the host's IPC namespace, and no history mount. Instead it runs with:

- `--network none`, so loopback is the only interface
- `--user sandbox`, an unprivileged, non-login user (uid 2000) whose home and working directory is `/sandbox`. `/home/sclaw` is mode 1770 with group `sclaw`, so it can't be read
- `--cap-drop ALL` and `--security-opt no-new-privileges`
- `--log-driver none`, whatever the daemon's default driver, so docker keeps no log of the container's main stdout and stderr. Any sandbox process can write to PID 1's stdout through `/proc/1/fd/1`, and for `sandbox exec --ephemeral` the command's own output is that stream, so a log would store untrusted bytes on the Docker host's disk outside `--disk` and `--memory`. Nothing is lost: a named sandbox's PID 1 is `sleep infinity`, `sandbox exec` output comes back over `docker exec`, and a one-off sandbox's output reaches the caller attached rather than through `docker logs`
- `--read-only`, with a 256 MB tmpfs at `/tmp` and a tmpfs at `/sandbox` (see [sandbox disk](#sandbox-disk)). Files are copied into `/sandbox` with [`sandbox cp-in`](#copying-files)
- `--memory 2g`, `--pids-limit 256`, `--cpus 1`, and `--disk 1g` by default, changeable with flags of the same name
- `HOME=/sandbox`, an empty `BASH_ENV`, and a `PATH` without sclaw's `~/.local/bin`
- the malware signature directory mounted recursively read-only at `/var/lib/clamav` (see [scanning for malware](#scanning-for-malware))

`safeclaw sandbox exec`, with or without `--ephemeral`, runs its command as `/bin/sh -c 'umask 022; exec "$@"' sh CMD...`, so files it creates are not world-writable whatever umask docker gives the command. Some Docker versions start `docker exec` processes with a umask of `0000` instead of the container's. The command and its arguments are passed to the shell as positional parameters, so they reach the command exactly as given.

By default `sandbox exec` replaces itself with docker, so the command's output reaches the terminal byte for byte, including any escape sequences that came from the untrusted files: file names in an archive tool's messages, or errors from `pdftotext` or a script that failed on a crafted file. With `--escape-controls`, safeclaw instead runs docker as a child and passes its stdout and stderr, kept apart, through the same escaping as docker errors (see [copying files](#copying-files)): anything `unicode.IsPrint` rejects other than newline and tab, carriage return and invalid UTF-8 included, is written as a Go escape such as `\x1b`. Escaping rather than dropping keeps what the command said visible. A UTF-8 character split across reads is held back until it is whole. safeclaw returns docker's exit code, or 128 plus the signal number when a signal killed docker, and forwards SIGINT, SIGTERM, SIGHUP, and SIGQUIT to it, except SIGHUP when safeclaw was started with it ignored, as under `nohup`, so it stays ignored by both. Docker runs in its own process group so a Ctrl-C reaches it once, through safeclaw, except with `-i` and a terminal on stdin, where it must stay in the foreground group to read it; there the terminal signals it directly and only SIGTERM and SIGHUP are forwarded. `--escape-controls` is refused with `-t`, since a TTY merges stdout and stderr and the programs that want one need their control characters. The flag is opt-in because escaping changes the bytes, so binary output should be piped without it.

With `-v`, which can be repeated, each host directory is mounted recursively read-only, whatever `ro` or `rw` its spec carries: safeclaw turns it into `--mount type=bind,src=...,dst=...,readonly,bind-propagation=rprivate,bind-recursive=readonly`, so every filesystem mounted below the host directory is read-only in the sandbox too. A plain `-v src:dst:ro` bind can't ask for that: docker makes its submounts read-only only on a best-effort basis, on Docker Engine 25 or later with Linux 5.12 or later and a runtime that supports it, and otherwise leaves them writable without saying so. `bind-recursive=readonly` fails closed instead: an older docker CLI doesn't know the option, and docker refuses to create the container on an older Engine or kernel or a runtime without recursive read-only mounts. Docker allows it only with `rprivate` propagation, which also keeps filesystems mounted on the host later from appearing in the sandbox writable. So the spec's options are limited to what such a mount can take: `rprivate`, `ro`, `readonly`, and `rw` change nothing, `consistent`, `cached`, `delegated`, and `default` are passed on as `consistency=`, and everything else is refused before docker runs, naming the option. That includes `z` and `Z`, since docker only relabels for SELinux with `-v` (label the host directory yourself, for example with `chcon -Rt container_file_t`), the other propagation modes, and `nocopy`, which only applies to named volumes. The host path must be absolute after `~` and `.` are expanded, since a bare name would be a named volume, and the container path must be absolute. Like sessions' mounts, one exposing the config directory is refused, and one exposing a container runtime socket gets a warning; see [volume mounts](#volume-mounts). Paths with commas or quotes are quoted in the `--mount` value, which docker reads as CSV. Two mounts at the same container path, or one at `/sandbox`, `/tmp`, or `/var/lib/clamav`, are refused before docker runs. Rerunning `sandbox run` starts a stopped sandbox or leaves a running one alone, and `-v`, any limit flag, or a `--variant` other than the sandbox's recreates it. The new sandbox keeps whichever of the old one's mounts, variant, and limits were not given again: any `-v` replaces all of the old mounts with exactly the ones given, and without `-v` every old mount is kept. The signature mount is not one of them: every new sandbox gets it from the current signature directory. `sandbox inspect` lists every mount, and `sandbox verify` checks each one.

### Command timeouts

`sandbox exec --timeout DUR`, with or without `--ephemeral`, runs the command under coreutils `timeout` inside the container: it gets SIGTERM after DUR and SIGKILL 5 seconds later, and `timeout` signals the command's whole process group, so children it started go too. With `-t`, `timeout` has to leave the command in the terminal's foreground group (`--foreground`), so only the command itself is timed out. Enforcing the limit inside the container means it holds even if safeclaw is killed, and killing the `docker exec` client alone would leave the command running in the sandbox.

Without `--timeout` (or `--escape-controls`), `sandbox exec` replaces itself with docker, but then nothing would be left to say why the command ended, so with `--timeout` safeclaw runs docker as a child instead, as `--escape-controls` does, with the same signal forwarding. Output still passes through byte for byte unless `--escape-controls` is also given. When the command was timed out, safeclaw prints `Error: the command timed out after DUR` and exits 124, as `timeout` does, whether it ended with SIGTERM or SIGKILL. A command that exits 124 on its own before DUR is reported with its own exit code. A command running with the sandbox user's privileges can still escape `timeout` (by leaving its process group, or killing `timeout` itself), so if docker is still running 5 seconds after the SIGKILL, safeclaw stops it: a one-off sandbox is removed, which ends everything in it, and for a named sandbox the `docker exec` client is killed and the error says the command may still be running there, since its other commands can't be told apart. `safeclaw sandbox stop` ends it.

### Command environment

`sandbox exec -e NAME=VALUE`, or `-e NAME` to take the value from safeclaw's environment, sets an environment variable for that command only, so a value such as an archive password needn't be a command argument, where `ps` on the host and in the container shows it. safeclaw writes the variables to a pipe and passes its read end to docker, which reads them with `--env-file /dev/fd/N`, so the values are never in docker's arguments, its environment, or a file on disk. They can still be read from inside the container by the sandbox user (from the command's `/proc/PID/environ`), which is the point, and, for `--ephemeral`, by anyone who can `docker inspect` the one-off container while it runs, since there they are part of the container's configuration. This needs Docker 23 or later, whose `docker exec` has `--env-file`.

Names must be letters, digits, and `_`, not starting with a digit, and each may be given once. `-e NAME` for a variable that isn't set is refused rather than left unset, so a missing password is an error instead of a prompt or a silent failure. For a value a caller has only some of the time, `--env-if-set NAME` (repeatable) passes NAME from safeclaw's environment exactly as `-e NAME` does when it is set, and leaves it out of the command's environment without an error when it isn't. A variable set to the empty string counts as set and is passed empty, as `-e NAME` passes it. A name may be given only once across `-e` and `--env-if-set`, so `-e NAME --env-if-set NAME` is refused. Both flags work with and without `--ephemeral`. Values must be UTF-8 without newlines, carriage returns, or NUL bytes, which an env file can't hold, and all of them together must fit in 8 KiB, so the pipe holds them before docker starts. Since sandboxes never receive secrets, the names of stored secrets, `CLAUDE_CODE_OAUTH_TOKEN`, and `GH_TOKEN` are refused (by `--env-if-set` whether or not they are set, as are invalid names), which stops `-e GH_TOKEN` from passing the caller's token in by mistake; pass a value meant for the sandbox under another name. Errors name the variable but never print its value.

### Sandbox disk

`/sandbox` is a tmpfs of `--disk` bytes (default `1g`), mode 0700 and owned by the sandbox user, so a tool that extracts an untrusted archive there gets "No space left on device" once it reaches the limit, whether or not the archive records or tells the truth about its uncompressed size, and a zip bomb can't fill the Docker host's disk. `--disk 0` is refused, since a tmpfs of size 0 has no limit. A docker volume would keep files across a stop, but volume size quotas only work on a few storage drivers (overlay2 on xfs with project quotas, for one) and not on Docker Desktop or OrbStack, so a tmpfs is the limit that works everywhere. This has three consequences:

- tmpfs pages count toward `--memory`, which is why its default is 2g: a full `/sandbox` and `/tmp` still leave about 750 MB for processes. When a sandbox's files and processes together go past `--memory`, the kernel swaps if the host allows it and otherwise kills the process that is writing, so the limit holds either way. Raise `--memory` along with `--disk`
- Stopping a sandbox empties `/sandbox`, as stopping a one-off sandbox removes it. Its size is kept, and it is still empty, mode 0700, and owned by the sandbox user when the sandbox starts again
- `docker cp` into `/sandbox` is refused, since docker writes it to the read-only root filesystem rather than the tmpfs. `sandbox cp-in` works

The limit counts blocks actually written, not a file's apparent size, so a sandbox can still create a sparse file far larger than `--disk` (`truncate -s 8E` works, as it does on `/tmp`). Reading such a file only yields zeros, and [`cp-out`](#copying-files) checks each file's declared size against `--max-size` before copying anything, so it never streams one to the host.

Sandboxes run the `sandbox` [image variant](#image-variants) unless the config file or `--variant` says otherwise, so the document extraction tools are already installed and never need the network or root.

The two types are kept apart. `safeclaw run`, the dashboard's start, and the API refuse a sandbox name, `safeclaw stop`, `rm`, and `attach` refuse sandboxes, and the `safeclaw sandbox` commands refuse interactive sessions. `safeclaw ls` lists both with a TYPE column, and `safeclaw sandbox ls` lists only sandboxes.

### Copying files

`safeclaw sandbox cp-in` and `safeclaw sandbox cp-out` move files into and out of a running sandbox without `docker cp`, which runs as root on the daemon side, leaves root-owned files with the host's mode, and copies whatever it is pointed at. Both stream a tar that safeclaw writes or reads itself through `docker exec --user sandbox` and the image's `/usr/bin/tar`, so a copy can only read and write what the sandbox user can, and a symlink planted by the untrusted side can't make it read `/home/sclaw` or anything else root can. A stopped sandbox is refused.

The sandbox side also controls what those commands write to stderr, and part of their stdout. Only the last 64 KiB of any docker command's stderr is kept, a command whose stdout safeclaw buffers (rather than streams, as cp-out's tar is) fails once it passes 64 MiB (8 MiB for cp-in's listing, 64 KiB for its `mkdir`, and 1 MiB for the `sandbox verify` probe, each of which is stopped once it passes its limit), and docker errors and every error the CLI prints have control characters escaped: anything `unicode.IsPrint` rejects other than newline and tab, including raw 8-bit C1 bytes, is written as a Go escape such as `\x1b`, so container output never reaches the terminal as escape sequences.

`cp-in NAME FILE...` checks every file before sending any: symbolic links and anything that is not a regular file are refused, and each file is opened without following links and checked to be the same file that was inspected. Files land in `--to` (default `/sandbox/in`, and always under `/sandbox`) as `N-name`, with N continuing after the highest number already there, so files with the same name from different folders never overwrite each other. Numbers above 999999999 are ignored, since no run of copies gets near them and only code in the sandbox could have made them, so names stay short and their numbers can't overflow, and a copy that would need a number past it is refused. The `ls -1A` listing the numbers come from is read into memory, so a listing over 8 MiB, as from a destination with tens of thousands of files or code in the sandbox writing to the exec's output, is refused, naming the directory, and so is more than 64 KiB from the `mkdir` before it. The numbers are picked under a lock file in `~/.config/safeclaw/copy/` kept for each sandbox, and tar's `-k` refuses to overwrite anything regardless. Code in a sandbox can stall the copy's execs and with them its lock, so a sandbox can only delay copies into itself, and a copy waiting on the lock gives up when its context ends, such as on Ctrl-C. Since the sandbox user extracts them, the files are owned by uid 2000, with mode 644. Like `sandbox exec`, cp-in's `mkdir`, `ls`, and `tar -x`, and cp-out's `tar -c`, run under `umask 022`, so the directories cp-in creates are mode 755 rather than world-writable on Docker versions whose `docker exec` gives a umask of `0000`. Each container path is printed, in the order given, and a path that is not printable text (a host file name with a newline or terminal escape, say) is printed as a Go-quoted string so it stays on one line and never reaches the terminal as escapes.

`cp-out NAME DIR HOST_DIR --only GLOB` keeps only the regular files directly in DIR whose names match one of the (repeatable) `--only` globs. Symbolic links, hard links, directories, devices, and anything in a subdirectory are dropped, and a name that appears twice is an error. GNU sparse entries are dropped too, since the tar reader would expand them to their logical size, so a tiny stream can't fill the host disk even with `--max-size 0`; the image's tar never writes them, since it isn't given `--sparse`. Since the names come from the untrusted side, a kept file whose name is not valid UTF-8, contains anything `unicode.IsPrint` rejects (control characters such as newlines and terminal escapes, format characters such as bidi overrides, and spaces other than a plain space), or starts with `-` refuses the whole copy, with an error naming it quoted. As in a shell, a name starting with `.` only matches a glob that starts with `.` too, so `--only '*'` never brings back hidden files such as `.envrc` - ask for them with a glob such as `.envrc` or `.*`. HOST_DIR must exist unless `--mkdir` is given (see below); an existing directory, or a symbolic link to one, is used as it is, and anything else is refused. Files are written to a temporary directory inside it with mode 644 (less the umask), and nothing is moved into place until the whole stream has arrived, stays within `--max-size` (default `1g`, `0` for no limit) and `--max-files` (default `1000`, `0` for no limit; empty files are free against `--max-size`, so this is what stops a sandbox from planting any number of them), and none of the names already exist. Without `--force` each file is moved with a rename that refuses to replace, so a file created in the meantime is never overwritten. `--force` replaces existing files, and a symlink itself rather than its target, but never a directory. Each host path written is printed, quoted like cp-in's when it is not printable. Before anything is placed, the files are scanned for malware outside the sandbox, and a flagged one refuses the copy; see [scanning for malware](#scanning-for-malware).

`--replace` is for fetching results again after another run in the sandbox, so HOST_DIR ends up with exactly the current matching files without removing and recreating it first. It implies `--force`, and also removes the regular files in HOST_DIR that match an `--only` glob (with the same rule for hidden files) but are not among the files copied. Files that match no glob, subdirectories and their contents, and anything else in HOST_DIR are kept, and since `--only` is still required, it never empties the whole directory. A symlink in HOST_DIR is never removed and never followed, even when its name matches a glob: one named like a copied file is replaced by that file, as with `--force`, and its target is never written, and any other is left alone. Nothing is moved or removed until the whole stream has arrived and passed every check, so a failed or interrupted stream leaves HOST_DIR as it was. Then each host file to be replaced or removed is first moved aside into the temporary directory, the new files are moved in, and the old ones are deleted with the temporary directory; if any move fails, the new files are removed and the old ones moved back. The `--max-size` and `--max-files` limits count only the files copied, not the ones removed.

`--mkdir` creates HOST_DIR, with its missing parents, when it doesn't exist, so callers don't need a `mkdir -p` first. There is no short alias. An existing HOST_DIR, or a symbolic link to a directory, is used as it is, with every rule above, `--force` and `--replace` included, as without the flag. A path that exists but isn't a directory, a symbolic link that doesn't lead to a directory (a dangling one included), and a missing path whose nearest existing parent is either of those are refused before anything is read from the sandbox, so nothing is ever created through a dangling link. A symbolic link among the existing parents is followed, as `mkdir -p` does, so the new directories are created in its target; nothing is created inside the new directories but the files, so no other link is involved. The directories are created only once every file has arrived and passed every check, the scan included, so a refused, failed, or interrupted copy leaves no new directories behind. Since HOST_DIR doesn't exist yet, the temporary directory is made in its nearest existing parent instead, which is on the filesystem the new directories will be on, and is removed when the copy ends. The missing directories are built inside it with mode 755 less the umask, the files are moved into the deepest, and the whole tree is moved into place with one rename that refuses to replace, so HOST_DIR appears complete or not at all. If something else created the top missing directory during the copy, that rename fails, nothing is placed, and the error says to copy again, which then uses the directory that now exists. With no matching files, `--mkdir` still creates an empty HOST_DIR.

### Scanning for malware

`cp-out` scans the files it is about to place with ClamAV, and `sandbox scan` scans files inside a running sandbox. Both use the signatures in `$XDG_CACHE_HOME/safeclaw/clamav` (`~/.cache/safeclaw/clamav` by default), which the `sandbox` variant's `clamscan` reads from `/var/lib/clamav`.

`safeclaw sandbox update-signatures` downloads them with freshclam in a short-lived container: the `sandbox` variant's checked image, the default bridge network, the host user's uid and gid with no capabilities and `no-new-privileges`, a read-only root with a small tmpfs at `/tmp` holding a freshclam config written there (the official mirror, no log file, no clamd to notify, databases tested before they are kept), no secrets, env file, ttyd, or published port, `--memory 3g`, and one writable mount: a staging directory created next to the signature directory. The staging directory is seeded with a copy of the current files, so freshclam only fetches what changed (about 110 MB the first time). Once freshclam succeeds and the staged files include a readable `main` and `daily` database, each regular file is renamed into the signature directory and files freshclam no longer keeps are removed; a failed or incomplete update removes the staging directory and leaves the old signatures as they were. Each file is replaced whole, so a scan running meanwhile reads the old or the new copy of it. Updates are serialized by a lock file next to the directory. The command prints the daily database's version and build date, which say how fresh the signatures are, and each database's version, signature count, and build date, read from the 512-byte header of each `.cvd` or `.cld` file on the host.

Every sandbox mounts the signature directory recursively read-only at `/var/lib/clamav`. safeclaw creates it, mode 755 with files 644 so the sandbox user can read them, before creating a sandbox, so sandboxes created before the first update see the signatures once it lands. Sandboxes created before this mount existed don't have it, and `sandbox scan` refuses them, naming `sandbox rm -f` and `sandbox run` to recreate them.

`cp-out` scans unless `--no-scan` is given. Before reading anything from the sandbox it checks that signatures are installed, refusing with a message naming `update-signatures` and `--no-scan` when they are not, and that the `sandbox` variant's image exists. Once every file has arrived in the temporary directory in HOST_DIR, or with `--mkdir` in its nearest existing parent (see [copying files](#copying-files)), each is hard linked (or copied, where the filesystem can't link) into a directory of its own under a numbered name, and that directory is scanned in a fresh one-off container: the `sandbox` variant's checked image, `--network none`, the host user's uid and gid with no capabilities and `no-new-privileges`, a read-only root with a 512 MB tmpfs at `/tmp` for clamscan to unpack archives into, no log, and only two mounts, both recursively read-only: the signatures and the files. It gets the sandbox's `--cpus` and `--pids-limit`, and the larger of the sandbox's `--memory` and 3 GB. So the scan sees exactly the bytes that will be placed, and nothing left running in the sandbox can change what is scanned or the result, which a scan inside the sandbox could not promise. The numbered names mean clamscan's output can't be confused by a file name, which the untrusted side chose.

clamscan runs with `--alert-exceeds-max=yes` and `--alert-encrypted=yes`, so a file over its limits (100 MB per file and 400 MB scanned within one, by default) or an encrypted archive or document is flagged instead of passing as clean. Each file's result is `clean`, `infected` with the signature name, or `error` with the reason: those two heuristics, a file clamscan could not read, or a scan that failed as a whole, such as one killed for running out of memory. Any result other than `clean` refuses the whole copy with an error naming each file and its result, before anything is moved into HOST_DIR, so a refusal changes nothing there, with `--force` and `--replace` too. `--allow-flagged` places them anyway. The signatures' version and date and each file's result are printed to stderr, while stdout keeps listing the paths copied, so scripts reading it are unaffected. No files means no scan.

Loading the database dominates each scan: with ClamAV 1.5 and the official databases of November 2026, a scan of a few small files takes about 8 seconds and peaks at about 1.1 GB of memory, page cache included. The databases keep growing, and the `/tmp` tmpfs counts toward the limit, so the scan container's floor is 3 GB. It is a limit, not a reservation, but a Docker Desktop VM needs that much free memory for a scan to finish.

`sandbox scan NAME PATH...` runs the same clamscan inside the running sandbox with `docker exec --user sandbox`, under `umask 022`, with relative paths under `/sandbox`. A directory gets a result for each file directly in it, as clamscan names it, and a path with no result, such as one that does not exist, gets `error` with clamscan's message. Results are printed one per line (result, then the path, quoted when it is not printable), or with `--json` as `{"schema", "advisory", "signatures": {"version", "date", "databases"}, "results": [{"path", "status", "signature", "reason"}]}`; fields may be added within a schema version, but are never renamed, removed, or given a new meaning without a new one. It exits 1 when any file is infected, otherwise 2 when any could not be scanned, and 0 when all are clean. It is advisory: it runs where the untrusted files are, as the user they run as, so anything they left running can change its result, as with `sandbox verify`'s live checks. A separate `safeclaw-scan` helper inside the sandbox was considered and not added: it would run in the same place with the same trust, and a host command shares cp-out's result parsing and signature reporting.

### Unpacking archives

The `sandbox` image variant links `/usr/local/bin/safeclaw-unpack` to the image's `safeclaw` binary, which runs as `safeclaw unpack` when called by that name, so callers share one tested way of opening untrusted archives instead of each writing its own around `7z x` or `unzip`. Callers keep their own policy, such as which archives to open and what to do with the results. It drives `7z` (or `7zz`) and needs no config directory, so unlike other commands it doesn't check one. Run it inside a sandbox: it limits what a hostile archive can do, but the sandbox is what contains 7z itself.

`safeclaw-unpack detect FILE` prints the archive format FILE starts like, from its first bytes: `zip`, `7z`, `rar`, `tar` (by its `ustar` magic at offset 257), `gzip`, `bzip2`, `xz`, or `zstd`, or `none`. It exits 0 for an archive and 5 for `none`, and runs nothing, so it doesn't need 7z. These are the formats `extract` unpacks nested archives in, found by the same code, so `detect` and the nested-archive check never disagree and callers don't need their own list of archive MIME types. Like `list` and `extract`, it follows a link to a regular file and refuses anything else, opening the file without blocking so a fifo can't hang it. `--json` prints `{"status":"ok","code":0,"type":"zip"}`, or `{"status":"not an archive","code":5,"type":"none"}`, or for a failure the same `status`, `code`, and `error` fields as `list` and `extract`.

`safeclaw-unpack list ARCHIVE` parses `7z l -slt` and prints one tab-separated line per entry: its type (`file`, `dir`, `symlink`, `hardlink`, or `special` for a device, fifo, or socket), its size (`-` when the format doesn't record it), its path, and its flags. The path is escaped as in a Go string: backslashes are doubled, and tabs, newlines, and anything else `unicode.IsPrint` rejects are written as escapes such as `\t` and `\x1b`, so a line always has four fields and never reaches the terminal as escape sequences. Flags are comma-separated, `-` for none: `ENCRYPTED`, `LINK`, `SPECIAL`, and `UNSAFE-PATH` for a path that is empty, absolute (with either slash), starts with a drive letter, has a `..` segment (splitting on either slash), is not valid UTF-8, or has control characters. The listing is parsed strictly: an entry that doesn't start with `Path`, repeats a property, or has a line that isn't `Key = Value` is an error rather than a guess, since a misread entry could hide a link. `--json` prints one JSON object with the paths unescaped and a null size when it is unknown.

`safeclaw-unpack extract ARCHIVE DEST` needs DEST to be missing or an empty directory, and not a symbolic link. It lists the archive first and refuses one with links, special files, or unsafe paths (`--drop-bad` leaves those entries out instead, extracting only the safe files by name, matched literally), one with encrypted entries and no password, and one whose listed size would take the total past `--max-size` (default `512m`). While 7z extracts, the total size of DEST is checked every 200 ms and 7z is stopped once it passes the limit, and it is checked again afterwards, since formats such as gzip may not record the size, or record it wrongly. After 7z exits, any symbolic link, special file, or file with more than one hard link it made is deleted, which rejects the archive unless `--drop-bad` is given (the listing didn't show it, so the listing can't be trusted), directories are made usable by their owner, files lose any setuid, setgid, or sticky bit and become readable and writable by their owner, and every path must resolve inside DEST. Each extracted file that starts like a zip, 7z, rar, tar, gzip, bzip2, xz, or zstd archive (one `detect` names a format for) is then unpacked the same way into `NAME.unpacked` next to it, or `NAME.unpacked-2` and so on when the archive already had that name, never merging into what it had. The nested archive is kept, its size counts toward the limit, and by default (`--nested fail`) its errors count like the outer archive's, naming it. A file 7z can't open as an archive is left as it is, and one past `--depth` (default `3`, `0` for none) is left packed and flagged `DEPTH-LIMIT`. On success every path in DEST is printed, with `UNPACKED` on each nested archive that was unpacked, followed by the dropped entries, flagged `DROPPED`. On any failure DEST is emptied without following links, and a rejected archive's offending entries are printed.

With `--nested keep-going`, a nested archive that fails is left packed instead of failing the extraction, so a caller can unpack a whole tree in one call and keep only its own policy, such as which top-level archives to open. The archive is flagged by how it failed: `REJECTED` (links, special files, or unsafe paths, in its listing or made by 7z), `NEEDS-PASSWORD`, `TOO-LARGE` (its listing, or what it extracted, would take the total past `--max-size`), or `FAILED` (corrupt, or 7z failed). Everything it extracted, its `NAME.unpacked` directory and any archives nested in it, is removed without following links, and its dropped entries and the failures below it are forgotten, so nothing from it is left behind. The size limit stays shared by the whole tree: a nested archive is checked against what is left of it, and the space one that failed took is given back to the archives after it. A failure deeper down leaves only that archive packed, so the archive holding it stays unpacked with it flagged. The archive given still fails the whole run for its own problems, as do I/O errors outside a nested archive and an interrupted run. The run exits 0 when the outer archive extracted, even with archives left packed, since everything that was kept is safe and the flags say what wasn't: callers that want to treat a packed archive as a failure check for the flags. The text output prints each archive left packed with its flag like any other path, and one `left packed:` line per archive on stderr with what went wrong. `--json` adds `nested_failures`, one object per archive left packed in the order they were tried, with its `archive` path relative to DEST, its `status` and `code` as its own failure would have had them, its `error`, and for a rejected one the offending entries under `rejected`, their paths under the `NAME.unpacked` directory that was removed. The key is left out when nothing was left packed.

Exit codes:

| Code | Meaning |
|------|---------|
| 0 | success, including `extract --nested keep-going` with some nested archives left packed and flagged |
| 1 | failed: 7z failed, the archive is corrupt, or a usage or I/O error |
| 2 | rejected: the archive has links, special files, or unsafe paths, or 7z made some |
| 3 | needs password: the archive is encrypted and no password, or the wrong one, was given |
| 4 | too large: the contents are over `--max-size` |
| 5 | not an archive: `detect` found no format, or 7z can't open the file for `list` or `extract` and it doesn't start like an archive |

For `list` and `extract`, "not an archive" is told apart from "corrupt" by two checks together. 7z runs first, since it opens many formats `detect` doesn't know, such as ISO images and cab files, and those are listed and extracted as usual. When 7z says it can't open the file as an archive, the file's first bytes decide: one that doesn't start like any format `detect` knows is not an archive (exit 5), and one that does, such as a truncated zip, is corrupt (exit 1). Any other 7z failure is exit 1 too. A nested file 7z can't open is never an error, with either `--nested` value: it only looked like an archive, and is left as it is, without a flag.

The password is read from `SAFECLAW_UNPACK_PASSWORD`, or the variable `--password-env` names, and removed from the environment before 7z starts. It is written to 7z's stdin, where 7z reads its password prompt, so it is never in an argument list that `ps` shows; pass it into a sandbox with `sandbox exec -e SAFECLAW_UNPACK_PASSWORD`. Without a password 7z's stdin is empty, so its prompt fails at once instead of waiting. A password with a line break is refused, since 7z reads one line. Every 7z run gets `-spd`, so names are never wildcards, and the archive is passed after `--` as an absolute path, so it is never read as a switch or a list file.

### Extracting text

The `sandbox` image variant also links `/usr/local/bin/safeclaw-totext` to the image's `safeclaw` binary, which runs as `safeclaw totext` when called by that name, so callers share one tested way of turning an untrusted document into text that is safe to read instead of each writing its own script around poppler and tesseract. Like `safeclaw-unpack` it needs no config directory, and it limits what a hostile file can do to the tools, but the sandbox is what contains them.

`safeclaw-totext FILE OUTDIR` needs OUTDIR to be missing or an empty directory, and not a symbolic link, as for `safeclaw-unpack extract`. The file must be a regular file, and its type comes from its first bytes, never its name: a PDF starts with `%PDF-`, or has it within its first 1024 bytes and isn't text (poppler skips that much junk); a PNG, JPEG, GIF, TIFF, BMP (with a valid header size after its `BM`), or WebP image is recognized by its magic; text is valid UTF-8 with no NUL bytes in its first 8 KiB, an empty file included. Anything else is unsupported.

A PDF's page count and page sizes are read with `pdfinfo -f 1 -l MAX`. pdfinfo prints the document's metadata first, and a crafted Title can hold line breaks that look like pdfinfo's own lines, so only the lines after its last `Pages:` line are read; nothing the file controls is printed after it. A PDF that needs a password (pdfinfo or pdftotext reports an incorrect password, or pdftotext exits 3 for the document's permissions) is refused as encrypted. One encrypted with only an owner password opens without one and is converted, with `encrypted` set in the report. Each page up to `--max-pages` (default `100`) is extracted with `pdftotext -layout -enc UTF-8 -f N -l N` into `pNNN.txt`, numbered from `p001.txt` and padded to the width of the last page's number when that is wider; the pages after the limit are skipped as one `page-limit` range. A page whose text has fewer than `--ocr-threshold` (default `10`) characters, not counting whitespace, is rendered with `pdftoppm -gray -png -singlefile` at `--ocr-dpi` (default `300`), lowered for a page whose longer side would pass 10000 pixels so a crafted page size can't make an enormous image, and OCR'd with `tesseract --dpi` in `--ocr-lang` (default `eng`). The OCR text replaces the page's text unless it has fewer characters, and `--ocr-threshold 0` turns this off. A page whose pdftotext run times out or fails is OCR'd the same way, unless OCR is off, and has no file when that fails too. Rendered pages go in a temporary directory outside OUTDIR, removed afterwards.

An image is OCR'd with tesseract into `ocr.txt`, and a text file is copied into `text.txt`. Everything written, from every tool and the text file alike, passes through the same filter: C0 and C1 control characters other than newline and tab, DEL, and the bidirectional formatting characters (U+061C, U+200E, U+200F, U+202A to U+202E, and U+2066 to U+2069) are removed, so a form feed between pages or a carriage return goes too, and bytes that are not valid UTF-8 become U+FFFD. The characters counted for the report and the OCR threshold are those left that are not whitespace.

Each tool runs with `--timeout` (default `1m`) of its own, with stdin from `/dev/null`, in a process group of its own; when the timeout passes the whole group is killed with SIGKILL, so a tool that forked can't outlive it. The tools are run directly, never through a shell, and file names reach them as absolute paths: after `--` for poppler, whose argument parser stops there, and first for tesseract, which takes no `--`, where an absolute path can't be read as an option. tesseract gets `OMP_THREAD_LIMIT=1`, so it doesn't start a thread per CPU. `--ocr-lang` must be language names joined with `+`, so it can't smuggle in another option or a path.

The report is printed as tab-separated lines: `type` with the type, the page count, and `ENCRYPTED` or `-`; a `page` line for each file written with the page, its character count, the file name, and `OCR` or `-`; and a `skipped` line for each thing skipped with its first and last page (`0` and `0` for the whole file), the reason, the tool or `-`, and a detail escaped as in a Go string, or `-`. `--json` prints one JSON object instead. `schema` is the version of the output: fields may be added within a version, but are never renamed, removed, or given a new meaning without a new one. Lists are never `null`.

| Field | Meaning |
|---|---|
| `schema` | `1` |
| `status`, `code` | The outcome and its exit code: `ok`, `failed`, `encrypted`, `unsupported`, `partial`, or `timed-out` |
| `error` | What went wrong, when the status is not `ok` or `partial` |
| `type` | `pdf`, `png`, `jpeg`, `gif`, `tiff`, `bmp`, `webp`, `text`, or `unknown` |
| `pages` | A PDF's page count, `1` for an image or text file, and `0` when unknown |
| `encrypted` | Whether a PDF is encrypted, readable or not |
| `files` | Each file written, in page order, as `page`, `path` (its name in OUTDIR), `chars` (characters not counting whitespace), and `ocr` (whether its text came from OCR) |
| `ocr_pages` | The pages whose file holds OCR text |
| `skipped` | Each thing skipped as `first_page` and `last_page` (both `0` for the whole file), `reason` (`encrypted`, `page-limit`, `timed-out`, `unsupported`, or `failed`), `tool` when a tool timed out or failed, and `detail`, for people rather than parsing |

Exit codes:

| Code | Meaning |
|------|---------|
| 0 | ok: every page was converted |
| 1 | failed: a tool failed on the whole file, the file is corrupt, a tool is missing, or a usage or I/O error |
| 3 | encrypted: the PDF needs a password, or its permissions don't allow extracting its text |
| 5 | unsupported: not a PDF, a supported image, or UTF-8 text |
| 6 | partial: text was written, but pages over `--max-pages`, or a page whose extraction or OCR timed out or failed, were skipped |
| 7 | timed out: pdfinfo, or tesseract on an image, ran past `--timeout`, so nothing was written |

1, 3, and 5 mean what they do for `safeclaw-unpack` (failed, needs a password, not a file it handles), and 2 and 4, its rejected and too large, are unused. On every exit but 0 and 6, OUTDIR is emptied without following links, while the report still says what was skipped and why; on 6 it keeps what was written.

#### Converting a folder

`safeclaw-totext --recursive SRC OUTDIR` converts every regular file under the directory SRC, so a caller with a whole extracted report doesn't have to walk it, run the tool once per file, rename the results, and write its own manifest. A link to SRC is followed, but no link under it is. The tree is walked in lexical order, each directory's entries sorted by name, and each regular file is converted exactly as a single file is, with the same flags and its own `--timeout` for each tool run. OUTDIR has the single-file rules (missing or an empty directory, and not a symbolic link) and also can't be SRC or inside it, so the outputs are never walked; SRC must not change during the run.

The results are written flat into OUTDIR, so `sandbox cp-out --only '*.txt'` copies them all: `NNN-NAME.pNNN.txt` for each PDF page, `NNN-NAME.ocr.txt` for an image, and `NNN-NAME.text.txt` for a text file. `NNN` is the file's index among the entries, zero-padded to at least three digits, and `NAME` is its path in SRC made safe with the same function `safeclaw-mail` uses for attachment names, so `a/b.txt` becomes `a_b.txt`. The index makes every name unique even when two paths make the same safe name. Files are created with `O_EXCL` and `O_NOFOLLOW`. A file whose conversion ends in anything but ok or partial leaves nothing in OUTDIR, as in single-file mode, and the run goes on.

`--max-files` (default `10000`) limits how many files are converted, and `--max-output` (default `512m`) the total size of the text files written, the manifest not included. A file past `--max-files` is skipped with the reason `file-limit`. A write that would pass `--max-output` stops the tool writing it at once rather than at its timeout, and the page being written is dropped: a PDF keeps its pages before it and skips the rest as `output-limit`, an image or text file is skipped, and every file after it is skipped as `output-limit` too.

Every file gets an entry, whether it was converted or not: a link is skipped as `link` and a FIFO, socket, or device as `special`, and a directory that can't be read gets a failed entry. The manifest is written to `OUTDIR/manifest.txt` and printed, as tab-separated lines with paths, errors, and details escaped as `safeclaw-unpack list` escapes paths. Every line after the first names its entry by the zero-padded index its outputs start with:

| Line | Fields |
|---|---|
| `tree` | the status, the number of entries, the bytes of text written, the expand manifest (`folded`, `none`, or `invalid`), and why it was invalid, or `-` |
| `file` | the index, the path in SRC, the status (`ok`, `partial`, `encrypted`, `unsupported`, `failed`, `timed-out`, or `skipped`), the type, the size, the page count, and flags: `ENCRYPTED`, `EXPAND-OUTPUT`, or `-` |
| `error` | the index and what went wrong, when something did |
| `container` | the index, then from `safeclaw-expand`'s manifest the kind, depth, outcome, flags, parent (or `-`), and error (or `-`) |
| `page` | the index, the page, its characters, the output file in OUTDIR, and `OCR` or `-` |
| `skipped` | the index, the first and last page (`0` and `0` for the whole file), the reason, the tool or `-`, and the detail or `-` |

A skipped entry's reason is `link`, `special`, `file-limit`, `output-limit`, `unpacked`, `expand-manifest`, or `missing`; the rest are a single file's reasons. `--json` prints one JSON object instead, `{"schema", "status", "code", "error", "warning", "expand", "expand_error", "output_size", "entries"}`, each entry being `{"index", "path", "size", "status", "error", "type", "pages", "encrypted", "files", "ocr_pages", "skipped", "expand_output", "container"}` with the single-file fields as above, `expand_output` the container whose `safeclaw-expand` output it is, and `container` that container's record from the expand manifest as it is there. It follows the same schema rules, and its lists are never `null`.

When SRC holds a `manifest.json` that `safeclaw-expand`'s own reader accepts (a regular file, not a link, of its schema, naming only clean paths inside SRC), it is folded in, so one manifest says what happened to everything. Its paths are only matched against the files the walk found; nothing is ever opened by a path the manifest names. Each email and archive's entry carries its record. One that was opened, whose directory is in SRC, is skipped as `unpacked`, since its files are converted instead and converting the raw `.eml` would repeat its text with the MIME encoding left in. One left packed, or with an outcome this version doesn't know, which the expand schema says to treat as left packed, is converted like any other file, so a rejected archive's entry shows both its outcome and `unsupported`. `manifest.json` itself is skipped as `expand-manifest`. An email's `body.txt` and `parts.txt`, which the helper wrote, are converted rather than skipped, since `body.txt` holds the email's text and is often the only text a report has, and flagged `EXPAND-OUTPUT`. A container the manifest lists that isn't in SRC gets an entry after the others, skipped as `missing`. A `manifest.json` that the reader refuses is reported on stderr and in the `tree` line, and SRC is converted as a plain folder, `manifest.json` included; this is safe, since nothing in SRC is treated differently.

`--replace` lets a rerun rebuild OUTDIR from the current tree, for a caller that converts again after `safeclaw-expand` opened more of it, without emptying OUTDIR first. It works only with `--recursive`, and only changes anything when OUTDIR is not empty: a missing or empty OUTDIR is converted into as without it. A non-empty OUTDIR must hold an earlier run's results, and since OUTDIR is written by code in the sandbox, that is checked rather than assumed from a name. Its `manifest.txt` must be a regular file, not a link, of at most 256 MiB, that is exactly what this version writes for a run that ended `ok` or `partial`: it is parsed, every field unescaped and checked, and written again, and the two must match byte for byte, so a hand-edited line, a changed field count, a renumbered entry, or a non-canonical escape is refused. Every output it lists must be a flat name in OUTDIR that starts with its entry's index and ends in `.txt`, never `manifest.txt` or the same name twice. Everything else in OUTDIR must be `manifest.txt` or a regular file it lists as an output; a listed output may be missing, since a caller may have removed some. Anything else, such as a file the manifest doesn't list, a directory, or a link, is refused rather than removed: a run never leaves anything unlisted, and the manifest vouches only for what it names, so removing the rest would let a planted manifest empty a directory the caller cares about. OUTDIR itself can't be a link, as without `--replace`, though links above it are followed. A refused OUTDIR is left as it was, exit 1.

The run then writes into a new directory beside OUTDIR, `.NAME.totext-*` in its parent, so the final rename stays on the same filesystem, with OUTDIR's permissions. Once the run has succeeded and written its manifest there, OUTDIR is checked again (the same directory, still holding only earlier results), and the two directories are swapped in one step with `renameat2(RENAME_EXCHANGE)` on Linux (`renamex_np(RENAME_SWAP)` on macOS). Where the filesystem can't swap, OUTDIR is moved aside into a new `.NAME.old-*` directory and the new one moved in, moving OUTDIR back if that fails. The earlier results are then removed without following links, so a link put in OUTDIR after it was checked removes only the link; if they can't all be removed, the run still succeeds and says where they are in a warning on stderr and in the JSON report's `warning`. A run that fails, is interrupted, or finds OUTDIR changed removes the new directory and leaves the earlier results exactly as they were. A run killed outright can leave the new directory beside OUTDIR, which a later run neither reads nor counts as part of OUTDIR.

Exit codes for `--recursive` are for the whole run:

| Code | Meaning |
|------|---------|
| 0 | ok: every file was converted, or skipped only as an opened container or the expand manifest |
| 1 | failed: a usage or I/O error, SRC isn't a directory, OUTDIR is not a missing or empty directory (or, with `--replace`, one holding only an earlier run's results) or is inside SRC, or the run was interrupted; OUTDIR is emptied without following links and no manifest is written, or with `--replace` OUTDIR is left as it was |
| 6 | partial: something wasn't converted in full: a file that was partial, encrypted, unsupported, timed out, or failed, a link or special file, a file past `--max-files` or `--max-output`, a container `safeclaw-expand` left packed, or one missing from SRC |

### Reading emails

The `sandbox` image variant also links `/usr/local/bin/safeclaw-mail` to the image's `safeclaw` binary, which runs as `safeclaw mail` when called by that name, so callers share one tested way of opening untrusted emails instead of each writing its own decoder. Like `safeclaw-unpack`, it needs no config directory, and it should run inside a sandbox. It is written in Go with the standard library's `net/mail` and `mime` packages and `golang.org/x/net/html`, and runs no other program.

`safeclaw-mail list FILE` prints the message's main headers (`From`, `Reply-To`, `To`, `Cc`, `Date`, `Subject`, and `Message-ID`, each occurrence in order) as `Name: Value` lines, then an empty line, then one tab-separated line per part: its ID, media type, decoded size (`-` for a multipart), original file name (`-` for none), and flags. The ID is `1` for the message's content, `X.N` for the Nth part of multipart `X`, and `X.1` for the content of nested message `X`. Header values have their RFC 2047 encoded words decoded, in any charset `golang.org/x/net/html/charset` knows, and then invalid UTF-8 becomes U+FFFD, tabs, line breaks, and other spaces become a plain space, and every other character `unicode.IsPrint` rejects is dropped, such as control characters, bidi overrides, and zero-width characters. The name is decoded the same way, including RFC 2231 parameters, and escaped as `safeclaw-unpack` escapes paths, so it shows exactly what the message said. Flags are comma-separated, `-` for none:

| Flag | Meaning |
|------|---------|
| `BODY` | a `text/plain` or `text/html` part that isn't an attachment and has no file name, whose text is in `body.txt` |
| `SKIPPED` | a body part of a `multipart/alternative` that another part was chosen over |
| `ATTACHMENT` | any other part, written to its own file |
| `NESTED-MESSAGE` | a `message/rfc822` (or `message/global`) part whose headers and parts were followed |
| `DEPTH-LIMIT` | a nested message past `--depth`, written as an attachment instead |
| `UNSAFE-NAME` | an attachment whose name had to be changed to make it safe |
| `BAD-ENCODING` | a part whose transfer encoding or charset couldn't be decoded in full, or an HTML body with a single token over 4 MiB; what could be decoded is kept |
| `MALFORMED` | a part with a Content-Type that can't be parsed (read as `application/octet-stream`) or a part header net/mail can't parse (kept whole as an attachment), or a multipart with no boundary, no delimiter, or no close delimiter; what could be read is kept |

`safeclaw-mail extract FILE DEST` has `safeclaw-unpack`'s rules for DEST: it must be missing or an empty directory, and not a symbolic link, and on any failure it is emptied without following links. It writes `body.txt`, with the main headers, an empty line, and the text of every body part in order, each after a blank line. For a nested message, a `---------- Forwarded message (part ID) ----------` line and its main headers come before its text. In a `multipart/alternative` the text of each alternative is held until the last one is read, then only one is used: the first that is itself a `text/plain` body part, else the last that has any body text, so the other alternatives' text never reaches `body.txt`. HTML is turned into text with the `golang.org/x/net/html` tokenizer, streaming, without building a tree: `script`, `style`, `noscript`, `template`, `title`, `iframe`, `object`, `svg`, and `math` are left out with their contents, block elements and `<br>` become line breaks, list items get a `- ` marker, whitespace is collapsed outside `<pre>`, an image's alt text is kept in brackets, and a link whose text isn't its address is followed by the address in angle brackets, so the text shows where a link really goes. Body text is decoded from its charset and then stripped: CRLF and lone CR become LF, invalid UTF-8 becomes U+FFFD, and control characters other than tab and newline, and the bidi marks, embeddings, overrides, and isolates, are dropped.

Each attachment is written as `N-NAME`, `N` counting attachments from 1 across the whole message, nested ones included, so two with the same name never collide. `NAME` is the decoded name made safe: slashes and backslashes become `_`, invalid UTF-8 becomes `_`, other spaces become a plain space, characters `unicode.IsPrint` rejects are dropped, runs of dots are shortened until no `..` is left, leading dots, dashes, and spaces and trailing spaces are trimmed, and it is cut to 100 bytes, keeping an extension of up to 16 bytes. An attachment with no name, or none left, is `N-attachment`, or `N-message.eml` for a message. Files are created with `O_EXCL`, so nothing in DEST is ever overwritten or followed. Every part, file name, and destination file is printed as `list` prints it, with a sixth field, the file it was written to in DEST (`-` for none). `--json` prints one JSON object instead: `{"status", "code", "headers": [{"name", "value"}], "parts": [{"part", "type", "size", "name", "flags", "file", "headers"}], "body"}`, with names unescaped, a null size for a multipart, and a nested message's main headers in its `headers`; a failure prints `{"status", "code", "error", "part"}`.

Transfer encodings are decoded leniently and streaming, the way mail readers do. Base64 skips anything outside its alphabet and adds missing padding; data after the padding, or a last group of one character, flags the part `BAD-ENCODING`. Quoted-printable is decoded without reading whole lines, so a line of any length works, and an `=` that starts no escape is kept as it is, flagging the part. An unknown encoding is read as it is, flagged. `7bit`, `8bit`, and `binary` are read as they are.

Parts are split on their boundary by `safeclaw-mail` itself, following RFC 2046: a delimiter is `--` and the boundary at the start of a line, optionally followed by `--` for the close delimiter, then spaces or tabs, then the end of the line, and the line break before it belongs to the delimiter. The preamble and the epilogue are ignored. Each part's header is read with `net/mail`, like the message's, rather than with `mime/multipart`, whose header parser follows HTTP's stricter rules: a part header with a raw control character or a field name with a space would fail there, ending the multipart and hiding the parts after it. With its own splitter, a part whose header `net/mail` can't parse is kept whole as an attachment flagged `MALFORMED`, and the parts after it are read as usual. A `multipart/digest`'s parts default to `message/rfc822`.

Everything is streamed and bounded, so a crafted message can't exhaust memory. Each header (the message's, each nested message's, and each part's) is read into memory up to 256 KiB, 1000 fields, and 64 KiB per line, and only then parsed. A message is limited to 1000 parts, nested messages included, and to 32 levels of nesting, counting multiparts and nested messages. Going over any of these rejects the message. The HTML tokenizer buffers at most 4 MiB for one token. `--max-size` limits the total of `body.txt`, the attachments, and the alternatives' text while it is held. `--depth` (default `3`, `0` for none) limits how many levels of nested messages are followed; deeper ones are written as attachments, flagged `DEPTH-LIMIT`, rather than rejected. A file is a message when it starts with a header (after an mbox `From ` line, if there is one) that has at least one of `From`, `To`, `Cc`, `Subject`, `Date`, `Message-ID`, `MIME-Version`, `Content-Type`, `Received`, `Return-Path`, `Sender`, or `Reply-To`.

Exit codes, reusing `safeclaw-unpack`'s where they mean the same thing:

| Code | Meaning |
|------|---------|
| 0 | success |
| 1 | failed: a usage or I/O error, or DEST is not a missing or empty directory |
| 2 | rejected: the message is over a limit on its structure: over 1000 parts, nested over 32 levels deep, or a header over 256 KiB, over 1000 fields, or with a line over 64 KiB |
| 3 | not used: it means needs password in `safeclaw-unpack`, which emails don't have |
| 4 | too large: what would be written is over `--max-size` |
| 5 | not a message: the file doesn't start with a message header |

### Opening a tree of emails and archives

Untrusted reports mix the two kinds of container: an email carries a zip, which holds a forwarded `.eml`, which carries another zip. The `sandbox` image variant links `/usr/local/bin/safeclaw-expand` to the image's `safeclaw` binary, which runs as `safeclaw expand` when called by that name, so callers can open such a tree in one call instead of writing their own loop around `safeclaw-unpack` and `safeclaw-mail`. Those two stay as they are for single files. It is built on the same Go packages, so an archive is opened exactly as `safeclaw-unpack extract` opens it and an email as `safeclaw-mail extract` does, and like them it needs no config directory and should run inside a sandbox.

`safeclaw-expand [IN...] DEST` has `safeclaw-unpack`'s rules for DEST on a first run: it must be missing or an empty directory, and not a symbolic link. A DEST that has a manifest is resumed instead, as described in [resuming a run](#resuming-a-run). Every input must be a regular file or a directory (a link to either is followed, since the caller named it); one that is missing or is neither fails the run before DEST is touched. Each input is copied into DEST as `N-NAME`, `N` counting the inputs from 1 and `NAME` its base name made safe as `safeclaw-mail` makes attachment names safe, so inputs never collide and DEST holds everything the manifest names, whatever the inputs were mounted from.

An input directory stands for every regular file directly in it, in sorted order of name, as if each had been given by name in its place, so `safeclaw-expand /sandbox/in /sandbox/tree` opens everything `sandbox cp-in` copied in without a shell to expand `/sandbox/in/*`. Links, subdirectories, and anything else in it are left out without being followed, and each is noted on stderr as `ignoring PATH: WHY`; a file listed in it is then opened without following a link, so one swapped for a link after it was listed fails the run rather than being followed. A directory with no files in it is no inputs, not an error. Each file is copied and deduplicated by content exactly as a file given by name is, so the same command line works on every run: a rerun copies in only the files that are new or changed. An input directory must not be DEST, hold DEST, or be inside it, compared with links resolved and, for a DEST that doesn't exist yet, its longest existing prefix resolved; either fails the run before DEST is touched, since a run would otherwise take its own copies for inputs. A run given inputs that turn out to be only empty directories still finishes: a first run makes DEST and writes a manifest with no inputs, which later runs resume from. A run given no inputs at all and with no manifest in DEST is still refused, since that is almost always a mistyped DEST. The manifest doesn't record that an input came from a directory: its copy's name, size, and `sha256` are what deduplication and a reader need, and a file given by name doesn't record where it came from either.

A container is a regular file that starts like an archive `safeclaw-unpack detect` names a format for, or, unless `--no-mail` is given, one that starts like an email: a header within `safeclaw-mail`'s header limits that parses and has one of the fields a message has, after an mbox `From ` line if there is one. A header over a limit is not detected, so a large file of other text is never taken for a rejected message. Each container is opened into `NAME.unpacked` next to it (`NAME.unpacked-2` and so on when that name is taken, never merging into what was there): an archive is listed, checked, extracted, and sanitized as `safeclaw-unpack extract` does, without unpacking the archives in it, and an email is extracted as `safeclaw-mail extract` does, into `body.txt` and `N-NAME` attachments, with its part listing, the lines `safeclaw-mail extract` prints, written to `parts.txt`. Then every regular file in that directory is looked at in turn, without following links, in sorted order, depth first, so each container is opened before the ones after it are looked at.

The helper's own output is never taken for an email: `body.txt` starts with the message's headers, so it would look like one. Rather than guess from the content, `safeclaw-expand` skips exactly the files it wrote itself, an email's `body.txt` and `parts.txt` at the top of its `NAME.unpacked`, and lists them as the container's `outputs` in the manifest. Everything else is the container's own content and is looked at: attachments are always `N-NAME`, so they can't take those names, and a `body.txt` that came out of an archive is checked like any other file.

`--depth` (default `3`, `0` for only the inputs) limits how many levels of containers are opened below the inputs, emails and archives alike. Inside an email, each forwarded message counts as a level: an attachment is one level below the email, and one more for each forwarded message around it, and the email's forwarded messages are followed only as deep as the tree's limit allows, so one past it is written as an `N-message.eml` attachment and flagged `DEPTH-LIMIT` there. `--max-size` (default `512m`) limits the total size of everything opened across the whole tree, `body.txt` and `parts.txt` included, the input copies not: each container is opened against what is left of it, checked again once it is opened, and the space one that failed took is given back to the containers after it. `--password-env` (default `SAFECLAW_UNPACK_PASSWORD`) is read and removed from the environment as `safeclaw-unpack` reads it, and is given to 7z for every encrypted archive in the tree. Without 7z on PATH, emails are still opened, and every archive is left packed and flagged `FAILED`.

Every level keeps going, the inputs included, as `--nested keep-going` does for nested archives. A container that is rejected (links, special files, or unsafe paths in an archive, or an email over a limit on its structure), needs a password, would take the total past `--max-size`, fails otherwise, or is past `--depth` is left packed, flagged `REJECTED`, `NEEDS-PASSWORD`, `TOO-LARGE`, `FAILED`, or `DEPTH-LIMIT`, and its `NAME.unpacked` is removed without following links, so nothing from it is left behind. Everything else is kept. A nested file that only starts like an archive, which 7z can't open, is left as it is and not recorded, as `safeclaw-unpack` leaves it; an input like that is corrupt, and `FAILED`. The run itself fails for an I/O error outside a container or an interrupt; a first run then empties DEST without following links.

When the run finishes it writes `DEST/manifest.json`, which doesn't count toward `--max-size`, and prints one tab-separated line per container: its kind (`email`, or the archive format), its path, its flags, and the directory it was opened into (`-` when it was left packed), with the paths escaped as `safeclaw-unpack list` escapes them. Each entry that got an archive rejected follows it on an `entry` line with its type, its path inside the archive, and its flags, and each container left packed for a failure is also reported on stderr with what went wrong. `--json` prints the manifest instead:

```json
{
  "schema": 1,
  "status": "ok",
  "code": 0,
  "options": {"depth": 3, "max_size": 536870912, "mail": true, "password": false},
  "size": 12345,
  "inputs": [{"path": "1-report.eml", "size": 4567, "kind": "email", "sha256": "9f86d0..."}],
  "containers": [
    {
      "path": "1-report.eml",
      "kind": "email",
      "depth": 0,
      "outcome": "unpacked",
      "flags": ["UNPACKED"],
      "unpacked": "1-report.eml.unpacked",
      "outputs": ["1-report.eml.unpacked/body.txt", "1-report.eml.unpacked/parts.txt"],
      "code": 0
    },
    {
      "path": "1-report.eml.unpacked/1-files.zip",
      "kind": "zip",
      "depth": 1,
      "parent": "1-report.eml",
      "outcome": "rejected",
      "flags": ["REJECTED"],
      "code": 2,
      "error": "rejected: 1 entry with links, special files, or unsafe paths",
      "rejected": [{"type": "symlink", "size": null, "path": "link", "flags": ["LINK"], "link": "/etc/passwd"}]
    }
  ]
}
```

`schema` is the manifest's version: fields, outcomes, and flags may be added within a version, but are never renamed, removed, or given a new meaning without a new one, so a reader should treat an outcome it doesn't know as a container left packed. `options` is the last run's policy, with only whether a password was given, and `hold`, the sorted hold kinds `--hold` gave, left out when it gave none. `size` is what counts toward `--max-size`. `inputs` are the copies, in the order the inputs were given across runs, with the kind of each that is a container and the SHA-256 of its content. `containers` has one record per container, in the order they were found, each before the containers found in it; a container opened by a later run keeps its place, and what is found in it comes after the records already there. Its `path` is the record's key: it is unique within a manifest and the same for the same inputs. `kind` is `email` or the archive format, `depth` its level (0 for an input), `parent` the container it was found in, `outcome` one of `unpacked`, `rejected`, `needs-password`, `too-large`, `failed`, `depth-limit`, `skipped`, or `held`, and `flags` the outcome's flag, then for an opened email `UNSAFE-NAME`, `BAD-ENCODING`, or `MALFORMED` when its parts had them, the details being in its `parts.txt`. `unpacked` is the directory it was opened into, `outputs` the files in it the helper wrote itself, `code` the exit code `safeclaw-unpack` or `safeclaw-mail` would have given for its own failure (0 when it didn't fail), `error` what went wrong, and `rejected` the entries that got an archive rejected. `skip` is the skip list, the paths `--skip` gave that no `--unskip` took off, found or not. Every `path`, `parent`, `unpacked`, `outputs`, and `skip` value is relative to DEST, uses slashes, and has no empty, `.`, or `..` elements, which the manifest is checked for before it is written and when it is read back; the paths under `rejected` are entry names inside the archive as it listed them, which can be unsafe, and are never paths in DEST. A failed run prints `{"schema", "status", "code", "error"}` and writes no manifest, leaving a rerun's manifest as it was. The manifest is written to a new file with a random name in DEST, which then replaces `manifest.json`, so a reader never sees part of one.

Exit codes:

| Code | Meaning |
|------|---------|
| 0 | the run finished, including with containers left packed and flagged |
| 1 | failed: a usage or I/O error, an input that is missing or not a regular file or a directory, an input directory that is DEST, holds it, or is inside it, DEST is not a missing or empty directory and has no manifest, the manifest was refused, another run is using DEST, or the run was interrupted |

Codes 2 to 5 are not used for the run. A finished run exits 0 however many containers were left packed, as `safeclaw-unpack extract --nested keep-going` does, since everything kept is safe and the manifest says what wasn't, and that holds for the inputs too: an input left packed is a container like any other. Each container's own failure keeps its `safeclaw-unpack` or `safeclaw-mail` code in the manifest's `code`, so a caller that wants to treat a packed container as a failure checks the flags or the codes.

To turn an opened tree into text, run `safeclaw-totext --recursive DEST OUTDIR`, which folds this manifest into its own; see [converting a folder](#converting-a-folder).

#### Resuming a run

Opening a report usually takes more than one run: list what would be opened and decide what to leave alone, open it, and open it again once a password turns up in an email body the first run decoded. `safeclaw-expand` keeps that state itself, in the manifest, so a caller expresses its decisions as flags instead of tracking outcomes in its own code.

The state is `manifest.json` rather than a separate file. It already records every container's path, outcome, depth, parent, and directory, and the size that counts toward `--max-size`, which is what a rerun needs, so a second file would duplicate it and could disagree with it; and a reader such as `safeclaw-totext --recursive` reads the same manifest, so it always sees the tree as the last run left it. What resuming adds to it is additive within schema 1: the `skip` list, each input's `sha256`, and the `skipped` outcome, and, for holding archives, `options.hold` and the `held` outcome.

Running `safeclaw-expand` on a DEST that has a manifest resumes from it, with or without new inputs. DEST is written by code in the sandbox, so the manifest is untrusted, and before anything is changed it is read and checked, holding an exclusive lock on DEST so two runs never share it (`--plan` takes a shared one). It must be a regular file, not a link, of at most 64 MiB, with valid JSON of schema 1 from a finished run, and pass the path checks above. Its records must fit together as a run writes them: every input is a top-level `N-NAME` with a valid `sha256`, every outcome is a known one with its own flag first and only an opened email's part flags after it, every code is one a container can have, a container with no parent is an input at depth 0, every other one is inside its parent's directory, deeper than its parent, and listed after it, and an opened container's directory is its own `NAME.unpacked` or `NAME.unpacked-N`, holding its outputs. A `skipped` container must be on the skip list. Every hold kind in `options.hold` must be a known one, sorted, without duplicates, and a `held` container must be an archive whose parent is an email, in a DEST whose `options.hold` has `mail-archives`, off the skip list, with no failure recorded. And the tree on disk must match it for everything a rerun relies on: each container left packed is reached from DEST only through directories, checked with `lstat` on every component so no link is followed, and is still a regular file that starts like the kind recorded. A manifest that fails any of this refuses the run, exit 1, saying which record failed and why, and nothing is changed.

A rerun keeps the containers already opened, rejected, skipped, held, or past `--depth` as they are. It opens again, in the manifest's order, the ones left `NEEDS-PASSWORD`, `TOO-LARGE`, or `FAILED`, with its own password and `--max-size`, along with any held one it releases and any skipped one `--unskip` took off the list, and each opened one's contents are looked at as usual. Then the inputs it was given are copied in, numbered after the ones already there, and opened as usual; an input with the same name and content as one already in DEST, by its `sha256`, isn't copied again, so a caller can rerun the same command line with a password added. That holds for the files in an input directory too, so rerunning `safeclaw-expand /sandbox/in /sandbox/tree` after another `sandbox cp-in` copies in only the new files. `--max-size` counts what is already in DEST, measured on disk rather than taken from the manifest: the size of every regular file in DEST, found without following links, except the input copies and the manifest. A container that fails again is recorded with its new failure.

`--depth`, `--no-mail`, and `--hold` are DEST's policy, set by its first run, and a rerun that gives others, or leaves out ones the first run gave, is refused with the flag it needs: opening deeper would leave the containers already flagged `DEPTH-LIMIT` packed while new ones at the same depth are opened, emails a first run left as plain files were never recorded as containers, and dropping a hold would open archives no one has seen the listing of, so none of these changes could be applied to the whole tree. They aren't taken from the manifest when a rerun leaves them out, since code in the sandbox could have changed it: every limit a run has comes from its own flags. `--max-size` is each run's own, its default included. The password is never recorded, only whether there was one.

`--skip PATH` (repeatable) adds PATH to the skip list, written as the container lines write it, escapes included, and `--unskip PATH` takes it off. A container on the list is left packed and flagged `SKIPPED` whenever a run finds it, unless it is past `--depth`, which flags it `DEPTH-LIMIT` as usual; one already rejected or past `--depth` keeps that outcome. A path no container has yet is kept on the list for a later run, and noted on stderr. Skipping a container that is already opened, unskipping a path that isn't skipped, or giving a path both ways fails the run with nothing changed.

`--plan` prints the containers not opened yet, without opening or changing anything: each left packed as its container line, in the manifest's order, then each new input that is a container, at the path it would be copied to, flagged `NEW`, or `SKIPPED` when the skip list has that path. One a rerun could open, flagged `NEEDS-PASSWORD`, `TOO-LARGE`, `FAILED`, `SKIPPED`, `HELD`, or `NEW`, is followed by its entries as `safeclaw-unpack list` prints them, each on an `entry` line (`entry`, TYPE, SIZE, PATH, FLAGS), listed with the run's password, or for an email by its parts as `safeclaw-mail list` prints them, each on a `part` line (`part`, PART, TYPE, SIZE, NAME, FLAGS). The rejected ones, and those past `--depth`, which a rerun keeps packed, are one line each. One that can't be listed, such as a 7z archive with encrypted headers and no password, is reported on stderr. `--plan --json` prints `{"schema", "status", "code", "containers"}`, each container its manifest record (with an empty `outcome` for a new input) and its `entries` or `parts`, as `safeclaw-unpack list --json` and `safeclaw-mail list --json` give them, or a `list_error`. `--plan` checks the manifest as a rerun does, refuses another `--depth`, `--no-mail`, or `--hold`, and can't be given `--skip`, `--unskip`, `--release`, or `--release-all`; with no manifest, DEST must be missing or empty, it plans the inputs given, and it makes nothing. Input directories are resolved as a run resolves them, with what is left out noted on stderr, and ones with no files in them plan nothing.

A rerun that fails, for an I/O error, a name an input copy needs being taken, or an interrupt, removes everything it added, newest first and without following links: the directories it opened containers into and the input copies it made. It leaves the manifest as it was, since the new one is only written once the run has finished, so DEST is as it was before the rerun. A first run that fails still empties DEST, and a DEST with no manifest must still be missing or empty.

#### Holding archives from emails

`--plan` lists an input email's parts and an input archive's entries before anything is opened, but an archive attached to an email is opened in the same run that opens the email, so its entries would never be shown before it is extracted, and skipping it would mean guessing the `N-NAME` the email's attachment will be written as. `--hold mail-archives` keeps the review policy, see every archive's listing before it is opened, a flag on the helper rather than code in the caller. `--hold` takes a kind so other kinds of hold can be added later; `mail-archives` is the only one, and an unknown kind is a usage error.

With it, emails are opened as usual, and every archive that came out of one is left packed and flagged `HELD`, recorded with the `held` outcome and no code or error. An archive came out of an email when the container it was found in is an email: an attachment of the email, or of a message forwarded in it, since `safeclaw-mail` writes those into the same `NAME.unpacked`, or of a forwarded message past the email's depth, which is written out as an `N-message.eml` email of its own. A container past `--depth` is flagged `DEPTH-LIMIT` and one on the skip list `SKIPPED` instead, as usual. A file in an email that only starts like an archive, which 7z can't list, is left as it is and not recorded, as when it isn't held; to tell, the archive is listed with 7z and the run's password, and one that can't be listed for another reason, such as encrypted headers, is held. Without 7z every archive from an email is held, and fails like any other once released.

`--plan` lists a held archive with its entries, as it lists a `SKIPPED` one. A rerun opens a held archive only when it releases it: `--release PATH` (repeatable), with the path as the container lines write it, or `--release-all`, which releases every held archive except the ones that run's `--skip` gives. `--skip PATH` on a held archive keeps it packed for good, flagged `SKIPPED`, and `--unskip PATH` on one the hold applies to holds it again rather than opening it, unless the same run releases it too. Anything not released stays held on every later run. A released archive is opened with the run's password and `--max-size`, and from then on is a container like any other: if it fails it is flagged as usual, and retried as a failed container is, with no further release.

Archives found inside a released or opened archive are opened as usual, since their parent's listing was already reviewed. An email found inside one is opened as usual too, since emails are never held, but the archives found in that email came out of an email, so the hold applies to them again and they are held until released. Inputs are never held, since `--plan` lists them before they are opened.

A release is checked against the manifest the way a skip is, before anything is changed: releasing a path no container has, or a container that isn't held, such as one opened, skipped, or flagged `NEEDS-PASSWORD`, giving `--release` and `--skip` for the same path, `--release` together with `--release-all`, or either without `--hold`, fails the run with exit 1 and nothing changed. `--release-all` with nothing held, including on a first run, is fine, so the same command line works on every run. `--hold` is DEST's policy, as described above: a rerun must give it, and one that leaves it out, or gives it on a DEST whose first run didn't, is refused.

### Opening a sandbox's files from the host

`safeclaw sandbox open NAME` runs `safeclaw-expand` and, with `--text`, `safeclaw-totext` from the host on fixed paths, so a caller doesn't build their command lines, pass the password, or empty the output folder itself. It runs `safeclaw-expand -- /sandbox/in /sandbox/tree`, which opens every file `cp-in` copied into `/sandbox/in` into `/sandbox/tree` and resumes the tree on a rerun, or `safeclaw-expand --plan -- /sandbox/tree` with `--plan`. `--skip PATH` and `--unskip PATH` pass through as `--skip=PATH` and `--unskip=PATH`, so a path that starts with `-` stays a value. With `--text`, once `safeclaw-expand` has finished, it runs `safeclaw-totext --recursive --replace -- /sandbox/tree /sandbox/out`, which replaces an earlier run's results only once the new ones are complete.

Before running anything it checks the options, that NAME is a running sandbox (an interactive session is refused, as for `cp-in`), and, with `docker exec --user sandbox`, that `safeclaw-expand`, and with `--text` `safeclaw-totext`, are on the sandbox user's PATH. The probe prints only the names it can't find, and any other output fails the check. An image without them, such as `base`, is refused with an error naming what is missing and saying to recreate the sandbox with `--variant sandbox`.

`--password-env NAME` reads NAME from safeclaw's environment and passes its value to `safeclaw-expand` as `SAFECLAW_UNPACK_PASSWORD` through a pipe on `--env-file /dev/fd/3`, as [`exec -e`](#command-environment) does, so it is never in docker's arguments, and `safeclaw-totext` never gets it. NAME unset, or set to the empty string, means no password, as `--env-if-set` leaves out an unset name, so the same command line works before and after a caller has one. NAME is checked as `--env-if-set` checks one, whether or not it is set: it must be a portable name and not a stored secret's, `CLAUDE_CODE_OAUTH_TOKEN`, or `GH_TOKEN`, and the value must be UTF-8 without newlines, carriage returns, or NUL bytes.

Each helper runs as `sandbox exec --escape-controls --timeout` runs a command: as a child of safeclaw, with stdout and stderr kept apart and control characters escaped, signals forwarded, and the run wrapped in coreutils `timeout` with `--timeout` (default `30m`, each helper getting its own), with the same backstop described in [command timeouts](#command-timeouts). The helpers' policy flags are registered on `sandbox open` with each helper's own type, default, and help, and passed through as `--NAME=VALUE` only when given, so the helper's defaults apply otherwise: `--depth`, `--max-size`, `--no-mail`, `--hold`, `--release`, and `--release-all` to `safeclaw-expand`, and `--max-pages`, `--ocr-threshold`, `--ocr-dpi`, `--ocr-lang`, `--max-files`, and `--max-output` to `safeclaw-totext`, which need `--text`. A rerun must give the tree's `--depth`, `--no-mail`, and `--hold`, as `safeclaw-expand` requires.

`safeclaw-expand` exits 0 whether or not it left containers packed, so `sandbox open` reads its container lines, after escaping, to tell: a container line (not an `entry` line) whose DIR is `-` is a container left packed, whatever its flags, `SKIPPED`, `HELD`, and `DEPTH-LIMIT` included, as `safeclaw-totext --recursive` counts them. The lines come from the sandbox, so code in it can make that answer wrong, which only changes the exit code. With `--text` a tree with containers left packed is converted anyway, since the files around them are worth reading, and the packed containers are listed in `/sandbox/out/manifest.txt`; when `safeclaw-expand` fails, times out, or is killed, nothing is converted and `/sandbox/out` is left as it was. The exit codes:

| Code | Meaning |
|---|---|
| 0 | Every container was opened, and with `--text` every file was converted (or `--plan` finished) |
| 1 | Failed before running a helper: a usage error, not a running sandbox, the image lacks the helpers, or docker failed |
| 2 | `safeclaw-expand` failed (with `--plan` too), leaving the tree as it was; with `--text` nothing was converted |
| 3 | `safeclaw-expand` left containers packed; with `--text` the tree was converted anyway, ok or partial |
| 4 | With `--text`, `safeclaw-totext` failed, so `/sandbox/out` is as it was |
| 5 | With `--text`, every container was opened but the conversion was partial |
| 124 | A helper ran past `--timeout`; when it was `safeclaw-expand`, nothing was converted |
| 128+N | A signal N killed docker, and nothing more was run |

A `safeclaw-totext` failure takes precedence over containers left packed, so 4 always means `/sandbox/out` wasn't rebuilt.

### Inspecting and verifying

`safeclaw sandbox inspect NAME` and `safeclaw sandbox verify NAME` let a script confirm that a container really is an isolated sandbox, and whether it is running, without relying on the `safeclaw-` prefix, the labels, or `docker inspect` templates. Neither changes the sandbox. Both refuse interactive sessions and missing names.

`safeclaw sandbox status NAME` answers only whether a sandbox is running, for scripts that don't want to parse JSON. It prints `running`, `stopped`, or `missing` and exits 0, 3, or 4. A sandbox counts as running when docker reports it running, the same as `inspect`'s `running`, and as stopped in every other state. A name that belongs to an interactive session prints nothing and exits 5 with an error, so a caller can refuse it instead of mistaking it for a missing sandbox, while a container labeled as neither a session nor a sandbox, an invalid name, or a docker failure exits 1. Like `inspect`, it runs nothing in the sandbox.

`inspect` prints the sandbox's docker configuration as JSON and runs nothing inside it. `schema` is the version of the output: fields may be added within a version, but are never renamed, removed, or given a new meaning without a new one. Lists are never `null`.

`inspect --field NAME` prints only one top-level field from the table below, on a line of its own: a string as plain text without quotes, and a number, boolean, list, or object as compact JSON, so `--field running` prints `true` or `false` and `--field limits` prints the limits object. A name that is not a top-level field, such as `limits.cpus`, is refused with the list of fields before docker is asked about the sandbox.

| Field | Meaning |
|---|---|
| `schema` | `1` |
| `name`, `container`, `id` | The sandbox name, its container name, and the container ID |
| `status`, `running` | docker's status (`running`, `exited`, ...) and whether it is running |
| `one_off` | Whether docker removes it when it stops |
| `variant` | Its image variant, `base` for the base image |
| `image`, `image_id` | The image tag it was checked and created by (from the `safeclaw.image` label, or docker's record for sandboxes created by tag before it) and the image ID it runs |
| `network_mode`, `networks` | docker's network mode (`none`) and the networks it is attached to |
| `user` | The user it runs as (`sandbox`) |
| `read_only_root`, `privileged` | `--read-only` and `--privileged` |
| `cap_drop`, `cap_add` | The capabilities dropped and added |
| `no_new_privileges` | Whether `no-new-privileges` is set |
| `ipc_mode`, `pid_mode` | docker's IPC and PID namespace modes |
| `log_driver` | docker's logging driver (`none`) |
| `limits` | `memory_bytes`, `cpus`, `pids`, and `disk_bytes` (the size of `/sandbox`), each `0` for none |
| `tmpfs` | Each tmpfs as `path`, `options`, and `size_bytes`, sorted by path |
| `mounts` | Each bind mount or volume as `type`, `source`, `destination`, `read_only`, and `recursive_read_only` (a read-only bind made with `bind-recursive=readonly`) |
| `labels` | Its `safeclaw.*` labels |

`verify` checks the guarantees above, first from the docker configuration: `network` (mode `none`, attached to nothing else), `user` (`sandbox`), `capabilities` (`ALL` dropped, none added, not privileged), `no-new-privileges`, `read-only-root`, `mounts-read-only` (every mount read-only, and every bind made with `bind-recursive=readonly`, which sandboxes created with `-v` binds by earlier versions fail until they are recreated, for example by running `sandbox run` again with their `-v`), `no-secrets` (no env var named after a stored secret, `CLAUDE_CODE_OAUTH_TOKEN`, or `GH_TOKEN`), `namespaces` (no host IPC or PID namespace), `limits` (memory, CPU, and process limits set), `logs` (log driver `none`, which sandboxes created before it was set fail until they are recreated, for example with `sandbox rm` and `sandbox run`), `disk` (a sized `/sandbox` tmpfs, mode 0700 and owned by uid 2000), and `tmp` (a sized `/tmp` tmpfs). Then `running`, and, for a running sandbox, a read-only probe run with `docker exec --user sandbox` that checks what the sandbox user actually gets: `live-user` (uid 2000), `live-home` (`/home/sclaw` can't be read or entered), `live-network` (only `lo`), `live-capabilities` (every capability set in `/proc/self/status` empty and `NoNewPrivs` on), `live-read-only-root` and `live-mounts` (`/`, each mount, and every mount point below each mount are `ro` in `/proc/self/mounts`, so a submount docker left writable fails), and `live-disk` (`/sandbox` is a single tmpfs no larger than `--disk`). A point mounted more than once counts as read-only only when every mount on it is. A stopped sandbox fails `running`, and its live checks are skipped, which also fails the verify. Each check is printed as `ok`, `FAIL`, or `SKIP` with what was found, and the command exits 1 with an error naming the failed checks. `--json` prints the report as `{"schema", "name", "container", "ok", "checks": [{"name", "ok", "skipped", "detail"}]}` instead, still exiting 1 when `ok` is false. Check names are stable within a schema version, and `detail` is for people, not parsing.

The checks from the docker configuration are authoritative: docker reports them, and nothing in the sandbox can change them. The live checks are advisory, since the sandbox can lie to them. The probe runs as the sandbox user, so code already running in the sandbox as that user can write to the probe's stdout through `/proc/PID/fd/1` or ptrace it, and make it report anything. The live checks catch a sandbox that docker set up differently from its configuration, not one that hides it. The probe's output is still parsed strictly: a section marker repeated or out of order, a repeated `uid`, `home`, interface, or status field, an unknown line, a mount line without its six fields, missing output, or anything after the closing `---end` marker fails every live check with `probe failed: output looks tampered with`, rather than letting a later line win, and more than 1 MiB of output fails them without being parsed. Output written to look exactly like the probe's can't be told apart. Running the probe in a fresh one-off container from the same configuration was considered and not done: it would check a new container rather than the running sandbox, which the configuration checks already cover, and it would mean creating a container, with the sandbox's host mounts, on every verify.

#### Verifying at creation

`sandbox run --verify` and `sandbox exec --ephemeral --verify` run the same checks once the sandbox has started, for callers that want a sandbox known to be isolated or none at all. The checks from the docker configuration can't change after creation, so verifying then covers the authoritative checks for the sandbox's whole life, and in a sandbox just created nothing has run yet that could tamper with the live checks.

With `sandbox run --verify`, when every check passes it behaves as without `--verify`, printing `Verified sandbox: all N checks passed` with its other progress (to stderr with `--rm`, so stdout still holds only the name). When any fails, the report is printed to stderr and it exits 1 with an error naming the failed checks. A sandbox this run created, or recreated because of `-v`, a limit flag, or `--variant`, is then removed. One that already existed, running or started again, is left as it was, since it is not this run's to remove, though it still exits 1. If safeclaw is interrupted (SIGINT or SIGTERM) between creating the sandbox and the end of the checks, the sandbox is removed too: `docker run` is allowed to finish, so the container is known to exist or not, and is then removed.

With `sandbox exec --ephemeral --verify`, safeclaw stays the parent of `docker run --rm --init` instead of replacing itself with it, and the command waits behind a gate: the container's command is `/bin/sh -c` with a script that waits for `/tmp/.safeclaw-verified` to exist, removes it, sets the umask, and replaces itself with the command (wrapped in `timeout` with `--timeout`). Meanwhile safeclaw waits for the container to be running, runs the checks, and only when every one passes creates the file with `docker exec --user sandbox ... touch`. Stdin given with `-i` waits in the container's stdin until the command reads it. When a check fails, the checks can't finish, or safeclaw is interrupted first, the container is removed before the command ever runs, the report is printed to stderr, and it exits 1 naming the failed checks. That includes a container an interrupted `docker run` created but never started, which docker's `--rm` would leave behind. If safeclaw dies without a chance to clean up, the gate gives up after 60 seconds and exits 125, so docker still removes the container. `--timeout` counts from when the command is let through, not from when the container started.

### One-off sandboxes

A one-off sandbox lives for exactly one job, so callers sharing the host need no locking, no detection of a sandbox recreated under the same name, and no per-job cleanup. If something removes one mid-job, the job is simply run again. One-off sandboxes are created with docker's `--rm`, so docker itself removes the container when it stops, and they get the same isolation, limits, and read-only `-v` as any other sandbox. Without `-s` they get a random `tmp-<8 hex>` name, and a name any container already has is refused rather than reused.

`sandbox run --rm --name-prefix PREFIX` names the sandbox `PREFIX-YYYYMMDD-HHMMSS` instead, for callers that want a name that sorts by creation time and can double as the id of the job's files on the host, such as `triage-20261128-110940`. The time is UTC, so names sort the same across time zones and DST changes, and it is read once per run. When a container already has that name, or docker refuses it because a container was created with it in the meantime, the run tries the name with `-2`, then `-3`, up to `-9`, and fails naming the range once all nine are taken. A name is checked before `docker run`, but docker's refusal of a duplicate name is what keeps two runs in the same second apart, so a run never takes over or removes the container that won the name, including one being verified when safeclaw is interrupted. The single-digit suffixes keep every name sorting after the one it was added to and before the next second's names. The prefix follows the session name rules, with one `safeclaw-` removed and letters lowercased as for `-s`, and can be at most 212 characters, so the longest name, with its timestamp and `-9`, is still within the 230-character limit on [session names](#session-names). `--name-prefix` can't be used with `-s`, which names the sandbox itself, or without `--rm`, since a named sandbox is reused by name and a timestamp would make every run a new one. `sandbox exec --ephemeral` doesn't take it.

- `safeclaw sandbox exec --ephemeral -- CMD` checks the image and name, then replaces itself with `docker run --rm --init` in the foreground (or, with `--escape-controls`, runs it as a child as described [above](#sandboxes), and with `--verify` as described in [verifying at creation](#verifying-at-creation)). Cleanup does not depend on safeclaw staying alive, the command's exit code is returned as is, `--init` forwards signals to the command instead of leaving it as PID 1, and nothing but the command writes to stdout
- `safeclaw sandbox run --rm` creates a detached one-off sandbox for jobs with several steps (`sandbox cp-in`, several `sandbox exec` calls, then `sandbox cp-out`). Progress goes to stderr and only its name to stdout, and `safeclaw sandbox stop` removes it

`safeclaw sandbox ls` marks them in a ONE-OFF column, and `safeclaw ls` lists their type as `sandbox (one-off)`.

#### Keeping a one-off sandbox's inputs

Running a job again is cheap for one command, but not for a long triage whose files came in over several `cp-in` calls and whose tree was opened with `--skip` and `--release` decided along the way. `sandbox run --rm --keep-inputs DIR` keeps a record of that on the host, and `sandbox run --rm --restore-from DIR` rebuilds the sandbox from it in a new one-off sandbox, which can be named with `-s` or `--name-prefix` as usual.

The record is only a record: it never holds a copy of a file, so no untrusted bytes are kept on the host beyond the caller's own originals, which the caller keeps. It is `DIR/inputs.json`, a JSON object with a `schema` (1), `verify` (whether the sandbox was made with `--verify`), `files`, and `opens`. Each file is `{"source", "sha256", "size", "path"}`: the absolute host path `cp-in` was given, the sha256 and size of the bytes it sent, which it hashes as it sends them, and the container path it wrote, `/sandbox/in/N-NAME`. Each open is `{"args": [...]}`, the `--skip`, `--unskip`, `--hold`, `--release`, `--release-all`, `--depth`, `--max-size`, and `--no-mail` flags of one `sandbox open` run, each as `--NAME=VALUE` exactly as it was passed to safeclaw-expand. The rest of a run's flags don't change the tree, and the password is never recorded. Fields may be added only with a new schema.

The record's location is kept on the sandbox itself, in a `safeclaw.keep-inputs` label holding DIR's absolute path, so `cp-in` and `sandbox open` find it without being told DIR again, and a sandbox made without `--keep-inputs` records nothing. A label was chosen over state on the host keyed by the sandbox's name because it is set by safeclaw when the container is created and can't change afterwards, nothing in the sandbox can read or alter it, it goes away with the container, and a later one-off sandbox that reuses the name can't inherit another job's record. Images can't carry it, since safeclaw refuses images with its labels.

- DIR is created mode 0700, with any missing parents, when it doesn't exist. An existing DIR must not be a symbolic link, must be owned by the caller, and must be mode 0700, and `--keep-inputs` refuses one that already holds a record, which `--restore-from` is for. Each use checks DIR again. The record is written before the sandbox is created and removed again when it can't be
- Every change to the record is made under a lock file in DIR, by reading and checking the record, changing it, and writing it to a temporary file in DIR that is synced and renamed over `inputs.json`, so a reader sees the old record or the new one and never part of one
- `cp-in` checks the record before copying anything, so a record that can't be read refuses the copy rather than leaving it unrecorded, and appends each file once the copy succeeds. If the record can't be written then, the paths are still printed and it exits non-zero saying the files were copied but not recorded. It refuses a `--to` other than `/sandbox/in`, the only place the record holds and the one `sandbox open` reads
- `sandbox open` appends its run once safeclaw-expand has finished, whether or not it left containers packed, since a run that failed left the tree as it was. `--plan` changes nothing and is not recorded. A run that can't be recorded exits 1 before safeclaw-totext, so the caller knows a restore won't replay it

The record is host-side and only safeclaw writes it, but a restore copies host files by what it says, so it is read as strictly as an expand manifest: at most 16 MiB, a regular file and not a link, no unknown fields or trailing data, the known schema, at most 100,000 files and 10,000 opens, each source a clean absolute path, each sha256 64 lowercase hex digits, each path directly in `/sandbox/in` and named `N-NAME` as `cp-in` names a copy of that source (N from 1 to 999999999 without leading zeros, NAME the source's base name), no path twice, and each open flag one of the recorded flags and printable text. Anything else refuses the restore, naming the problem, before anything is created.

A restore then opens each recorded source as `cp-in` does, refusing a link or anything but a regular file, and hashes it. If any source is missing, is no longer a regular file, or has another size or sha256, it refuses with one error naming each such source and creates nothing. The sources are only hashed and copied, never opened in any other way, so a restore reads no file's contents beyond hashing them. It then creates the sandbox, verified when the record or `--verify` asks for it, and copies the files back into `/sandbox/in` under their recorded names in one extraction that refuses to overwrite anything, hashing them again as they are sent. If the copy fails, or a source changed between its check and its copy, the new sandbox is removed. The new sandbox keeps recording to DIR, so later `cp-in` and `sandbox open` calls append to the same record, and `cp-in` numbers new files after the restored ones. `--variant`, `-v`, and the limits are not recorded, and apply as given to the restore.

A restore doesn't run `sandbox open` itself. The recorded runs are printed to stderr, in order, as `safeclaw sandbox open NAME FLAG...` commands, quoted for sh, for the caller to run again, adding `--password-env` where one needed a password. They are replayed one by one rather than merged into one command because safeclaw-expand refuses a release on a first run and a release with a skip of the same path, so only the original order rebuilds the same tree. Leaving them to the caller means a restore never runs the helpers on untrusted files without being asked, and the caller can pass the password and its own `--timeout` again.

### Stopping and removing

`safeclaw sandbox stop` and `safeclaw sandbox rm` take one name and, without `--missing-ok`, fail for a name with no container. Cleanup that runs whether or not a sandbox survived, for example after Docker restarted, can pass `--missing-ok` instead of checking `sandbox status` first: `stop` then exits 0 without running `docker stop` when there is no container by that name or it is already stopped, and `rm` exits 0 when there is no container by that name. Either prints which case applied (`Sandbox "NAME" is missing, nothing to stop`, `... is already stopped, nothing to stop`, or `... is missing, nothing to remove`) on stderr, so stdout stays empty. A one-off sandbox that docker removes between the lookup and the `docker stop` or `docker rm`, which docker reports as no such container or a removal already in progress, counts as missing too (recent docker's `rm -f` doesn't fail for a container that is gone, so `rm -f` then exits 0 without saying so). Any other docker error still fails. A name that belongs to an interactive session is still refused, with or without the flag, so the flag never hides a mistake about which container was meant. `--missing-ok` doesn't stand in for `-f`: `rm --missing-ok` still refuses a running sandbox, and `rm -f --missing-ok` removes it whether it is running or stopped and exits 0 when it is gone.

## Offline sessions

`safeclaw net off NAME` takes an interactive session off the network while it handles something untrusted, and `safeclaw net on NAME` brings it back. Taking a session offline disconnects it from every network it is attached to, which also takes down its ttyd web terminal, since the published port belongs to the container's network. Claude Code keeps running but can't reach the API until the session is back.

The networks are saved before anything is disconnected, along with any aliases, static addresses, and links (leaving out the aliases docker adds itself), so `net on` restores exactly those. The state is kept in `~/.config/safeclaw/network/NAME.json` (honoring `XDG_CONFIG_HOME`), not in the session's history directory, because that directory is mounted into the container. It records the container ID, so state left by a session that was removed and recreated under the same name, for example by `safeclaw rm` or `safeclaw build --recreate`, is ignored and deleted rather than applied to the new container. Without saved state, for example after a raw `docker network disconnect`, `net on` reconnects the session to the network it was created with: the [session network](#session-network), or `bridge` for sessions created before it.

Each `net off` records a hold with its `--owner`, an optional `--reason`, and when it was taken. Without `--owner` it takes the unnamed hold, which every caller without an owner shares. Taking an offline session offline again adds a hold, or updates the same owner's, and keeps the saved networks. `net on` releases only the hold for its `--owner` (or the unnamed one), fails if other owners hold the session and it holds nothing, and reconnects the session only once no holds remain, so one job can't bring a session back online while another still relies on it being offline. `--force` releases every hold. Every network change and state write happens under one lock file in that directory, so concurrent safeclaw processes don't interleave.

If a disconnect fails, `net off` still tries the session's other networks, then retries the failed ones once. If the session is still attached after that, the hold is kept rather than rolled back, since rolling back would bring the session online while its owner expects it offline, and `net off` fails naming the networks still attached, so it can be run again.

The status comes from docker: a session attached to no network is offline. `safeclaw ls` shows it in a NETWORK column (`online`, `offline` with its holders, `none` for sandboxes, or `host`), and the dashboard shows an `offline` badge. A held session that is still attached shows as `online` with its holders.

While a session is offline, or held offline but still attached:

- `run` and the dashboard's start still start or refresh it, warning that the web terminal is unreachable, and a started or running held session is disconnected again from any network attached to it
- `run` refuses to recreate it for a new `-v`, `--variant`, set of secrets, `--host-ipc` or `--no-memory` choice, or `--fresh-history`, so it can't come back online as a new container. `run` and the dashboard's start also refuse a session still published on `127.0.0.1` that they would move to `[::1]`, until `net on`
- `safeclaw build --recreate` skips it, checking under the network lock just before each removal, and the stale report marks it `(offline)`
- `safeclaw url` and the dashboard's terminal relay refuse it, so a held session that is still attached is not reachable through them either

A session held offline can't be removed: `safeclaw rm`, the dashboard's delete, and `/api/delete` refuse it, naming its holders, so removing it can't take it from a job that relies on it being offline. `safeclaw rm --release-holds` removes it anyway, releasing every hold. A session that is offline without holds, for example after a raw `docker network disconnect`, is removed as before. `rm` checks the holds and removes the container, its saved state, and its ttyd credential under the network lock, which `run` and `net off` take too, so a container created and taken offline under the same name meanwhile keeps its hold. State that belongs to a container that has the session's name once the old one is removed, such as one created outside safeclaw, is kept.

The saved state fails closed: if it can't be read, for example because it is corrupt, the session may be held, so `run`, the dashboard's start, `net off`, `net on`, `url`, the terminal relay, and `rm` refuse it with an error naming the file, `safeclaw build --recreate` skips it, and `safeclaw ls` shows it held by `unknown`. Fixing or removing the file brings it back, and `safeclaw rm --release-holds` removes the session along with the file.

Sessions using host networking, or sharing another container's network, can't be disconnected, so `net off` refuses them. Sandboxes always run with `--network none`, so the `net` commands refuse them too.

## Image variants

An image variant is the base `safeclaw` image with extra apt packages or `run` commands, tagged `safeclaw:NAME`. Variants come from two places:

- built in: `sandbox` adds poppler-utils, tesseract-ocr and tesseract-ocr-eng, 7zip, and file, and links `safeclaw-unpack` (see [unpacking archives](#unpacking-archives)), `safeclaw-totext` (see [extracting text](#extracting-text)), `safeclaw-mail` (see [reading emails](#reading-emails)), and `safeclaw-expand` (see [opening a tree of emails and archives](#opening-a-tree-of-emails-and-archives))
- `~/.config/safeclaw/config.yaml` (honoring `XDG_CONFIG_HOME`), whose `variants` map adds variants or replaces a built-in of the same name, and whose `defaults` pick the variant each session type uses when none is given (`base` for sessions and `sandbox` for sandboxes unless set)

The config file is decoded strictly, so unknown keys are errors. Names are lowercase and may not be `base`, which means the base image, or `latest`. Package names are checked, and `run` commands are one line each and run as root. The file is read whenever a variant is resolved, so the dashboard sees edits without a restart, and commands that don't resolve variants, like `ls`, `stop`, and `rm`, don't read it.

Each variant is built from a generated Dockerfile (`safeclaw variant dockerfile NAME`) that starts `FROM` the image in its `BASE` build argument, the local `safeclaw` image by default, installs the packages and runs the commands as root, then switches back to `sclaw` and labels the image `safeclaw.variant=NAME`. Each command is written as an exec-form `RUN ["/bin/sh","-c","..."]` with `<` escaped, so a trailing backslash or a heredoc in a command can't continue into the `USER sclaw` line and leave the image running as root. `safeclaw build` builds the base image, then each `--variant` and every variant already present locally, so no variant is left on an older base. `safeclaw pull` does the same with the published images: the unmodified built-ins are pulled from `ghcr.io/josegonzalez/safeclaw:<version>-NAME` (`:NAME` for latest), and variants from the config file are built on the pulled base. With `--verify`, each published image's tag is first resolved to its manifest digest with `docker buildx imagetools inspect`, `gh attestation verify oci://ghcr.io/josegonzalez/safeclaw@DIGEST --repo josegonzalez/safeclaw --signer-workflow josegonzalez/safeclaw/.github/workflows/release.yml` checks that the release workflow attested that digest, and the image is pulled and tagged by the digest rather than the tag, so a tag moved after the check can't swap in another image. It refuses before pulling anything when `gh` is missing or not logged in, and stops at the first image that fails, so a failing variant leaves the base image already pulled.

Containers on a variant carry the `safeclaw.variant=NAME` label; containers without it run the base image. An existing container keeps its variant unless `--variant` names a different one, which recreates it. A missing variant image is an error naming the `pull` and `build` commands that fetch it, and after a build or pull, containers whose variant image changed or no longer exists are reported as stale.

## Authentication

All secrets are stored on the host, and each becomes an environment variable of the same name.

### Where secrets are stored

Secrets are kept in the system keychain with [go-keyring](https://github.com/zalando/go-keyring): the macOS keychain, Secret Service on Linux, or the Windows credential manager. Each secret is an item under the `safeclaw` service, with the env var name as its account. The keychain can't list items or say when they were written, so a reserved `.index` item holds each secret's name and the time it was set. `~/.config/safeclaw/secrets.lock` is locked while the index changes, so the CLI and dashboard don't lose each other's writes. On macOS, values are passed to `security` on stdin, not in its arguments.

If the keychain can't be read, such as on a Linux server without Secret Service, secrets fall back to files in `~/.config/safeclaw/.secrets/` (one 0600 file per secret, named after it, with its modification time as the set time), with a warning. Only regular files are secrets: the store checks each name itself and opens files with `O_NOFOLLOW`, so a symlink, directory, or FIFO in the directory is treated as not set, and a name like `../x` is refused. A secret is written to a new 0600 temp file in the directory and renamed into place, so it never takes an older file's mode and replaces a symlink rather than writing through it. The directory is created with mode 700, and an existing one with looser permissions is tightened to 700 when the store is opened or written. When the keychain is available, files left there by earlier versions are moved into it with their modification times, deleted, and the directory removed once empty. Files whose names aren't valid env var names are left in place.

### How env vars are passed

1. `safeclaw run` renders each secret the session receives as `export NAME='value'` (shell-quoted) and pipes it into the container over stdin, as root, into `/etc/safeclaw/env`. Secret values never appear in process arguments.
2. `BASH_ENV=/etc/safeclaw/env` (set in the Dockerfile) ensures every bash invocation sources it
3. `.bashrc` also sources it for interactive shells, which don't read `BASH_ENV`

This means env vars are available everywhere - interactive shells, Claude's bash commands, and `docker exec bash -c` commands.

The env file, the auto memory setting, the terminal credential, and the credential ttyd's check sends curl all go into the container this way, so none of them can hang a run. safeclaw closes docker's stdin as soon as the input is written, but a command like `cat > /etc/safeclaw/env` only ends once docker passes that close on to it, and a run once hung there until its test timed out. So the command reads its input through `/bin/dd bs=1 count=N`, with N the input's length, which ends its stdin after the last byte whether or not docker passes the close on, and an empty input runs without `-i`. Each of these execs also has 30 seconds, and one still running then fails the run with an error naming the step, such as `writing the env file in safeclaw-work: timed out after 30s`.

The env file is created by the image owned by root with group `sclaw` and mode 640, so sclaw can read it but not change it, and the `sandbox` user can't read it. safeclaw rewrites its contents in place with `docker exec -u root` and never chowns it, since root has no capabilities in a session. Between runs, the agent can't add to it, for example an `export CLAUDE_CONFIG_DIR=...` that every later shell and Claude Code itself would pick up. The agent can still set `BASH_ENV` or any other variable in a shell it starts, but that only changes its own processes, which already run as sclaw: ttyd, tmux, Claude Code and every `docker exec` get `BASH_ENV` from the image, and nothing safeclaw runs reads a file sclaw controls.

Containers from images that predate the root-owned env file are told apart by whether `/etc/safeclaw/env` exists, and keep getting sclaw's `~/.env`, written as sclaw with mode 600, and the git identity in `~/.gitconfig`, until they are recreated from a current image. A failed check fails the run, rather than writing secrets to a file the container doesn't source.

### Choosing secrets

Because every bash process in a session can read the env file, each session can be limited to the secrets it needs. `--secrets A,B` writes only the listed secrets, `--no-secrets` writes none, and `--all-secrets` writes every secret, including ones added later. New sessions get every secret unless told otherwise.

The choice is recorded in the `safeclaw.secrets` container label as comma-separated names, so the container itself can't change it. Containers without the label, including ones created before it existed, get every secret, and an empty label means none. Without a flag, `run` and the dashboard's start keep the container's set; a different one recreates the container, since labels can't change. The set is also in the session's [kept choices](#kept-choices), so a session whose container was removed (for example by `safeclaw rm` or `safeclaw build --recreate`) gets the same set when it is created again without a flag. One with no kept choices, such as one removed before they were kept, gets every secret, with a warning when its history directory shows it existed before.

The env file is replaced on every run, so secrets left out of the set are removed from it. Names given on a run must be stored secrets, by the same rule used when the env file is written, so an entry the store doesn't count as a secret fails the run instead of being skipped (after prompting for the Claude and GitHub tokens, if the session receives them). A remembered name that has since been deleted is skipped with a warning, so the session still starts. Tokens the session doesn't receive are neither required nor prompted for. Without `CLAUDE_CODE_OAUTH_TOKEN`, a warning says Claude Code won't be logged in.

Sandboxes never receive secrets, whatever their labels say.

### Reused history

A session's history directory is kept when its container is removed or recreated, and it holds Claude Code's transcripts and the memory loaded into its system prompt. So a session whose secrets change keeps what its previous container wrote with the old set: a narrowed session can read transcripts written with more secrets, and a session with none can leave memory for a later one with every secret. When a container is created over existing history with a different set of secrets than the container it replaces or the session's [kept choices](#kept-choices), or with a chosen set where no earlier container's set is known, `run` prints a warning naming `--fresh-history`.

`--fresh-history` on `run` or `new` renames the history directory to `NAME.old-TIMESTAMP` next to it, with the time in UTC as `20261127T150405+0000`, and recreates an existing container, so the new one starts with an empty history. Nothing is deleted. The `+` and uppercase `T` can't appear in a session name, so a moved directory is never another session's history. If the new container can't be created, the history is moved back before the old container is restored. Like other recreates, it is refused while the session is offline.

### Claude Code

The token from `claude setup-token` is stored as `CLAUDE_CODE_OAUTH_TOKEN`. `safeclaw auth login` creates it without Claude Code on the host: it starts a container from the base image with no secrets, mounts, or ports, with `--cap-drop ALL` and `--security-opt no-new-privileges` like sessions, named `safeclaw.auth.` and a random suffix and labeled `safeclaw.auth` with a random owner ID, and runs `claude setup-token` there under `script`, attached to the terminal. Before starting the container, the login creates `~/.config/safeclaw/auth/OWNER.lock` (honoring `XDG_CONFIG_HOME`) and holds a lock on it until the container is removed. The sign-in can't call back to the host, so Claude Code prints a URL and asks for the code shown after signing in. Once it exits, the recording is read back and deleted from the container right away, terminal escapes are stripped, the last `sk-ant-oat01-` token is stored, and the container is removed, then the owner file. The container is also removed when the sign-in fails, on Ctrl-C or SIGTERM, and when the terminal closes (SIGHUP, unless safeclaw was started with it ignored). A login killed before cleaning up, for example with SIGKILL, leaves its container behind; every `safeclaw auth` command removes containers with both the name and the label whose owner file is missing or no longer locked, with one `docker ps`. The kernel releases the lock when the login's process exits, so a reused PID can't keep a container, with the token's recording, alive. Sign-in containers labeled with a PID by earlier versions are removed the same way, since their PID can't tell a live login from a reused one. Sign-in containers left by versions that didn't name them are not removed, and can be removed with `docker rm`. `safeclaw auth set` and `safeclaw env set NAME` read a value from stdin (or a hidden prompt on a terminal), so values never appear in process arguments.

Tokens are valid for a year, and the token doesn't say when it was made, so the expiry is estimated from when it was stored. `auth status`, `run` (for sessions that receive the token), and a dashboard banner warn in the last 30 days, and once it has expired. `run` only prompts for missing tokens when stdin is a terminal; otherwise it fails like `new`, with an error naming `safeclaw auth login` and `safeclaw auth set`.

The Dockerfile sets `hasCompletedOnboarding: true` in `.claude.json` to skip the onboarding flow. Without this, interactive mode ignores the token and shows the login screen ([known issue](https://github.com/anthropics/claude-code/issues/8938)). It also pre-accepts the home folder trust prompt and the bypass permissions prompt, which newer Claude Code versions show on every start.

Known limitation: the token from `setup-token` has limited scopes (`user:inference` only), so `/usage` doesn't work and the status bar shows "Claude API" instead of the subscription name ([#11985](https://github.com/anthropics/claude-code/issues/11985)). Chat works fine.

### GitHub CLI

`GH_TOKEN` is used for GitHub CLI authentication. On container start, `run` also configures the git user (name and email) from the GitHub account. It does this as root, reading `GH_TOKEN` from the env file, so `gh` uses root's home rather than sclaw's gh config, and writes the identity to the system config, `/etc/gitconfig`, along with `gh auth git-credential` as git's credential helper for `https://github.com`, so git uses `GH_TOKEN` to push and pull over https. `~/.gitconfig` is an empty root-owned file and `~/.config/git` an empty root-owned folder, so the agent can't add a global git config with options such as `core.fsmonitor` or `core.pager` that run commands. `git config --global` fails with a permission error, so tools that write the global config, such as `gh auth setup-git`, don't work, and aren't needed for GitHub; a repository's own `.git/config` can still be changed. `~/.config` is root:sclaw 1770 like the home folder, so other tools can still keep their config there.

We recommend creating a separate GitHub account for SafeClaw so you can scope its permissions independently.

## Image

The image has two users: `sclaw`, who runs Claude Code, and `sandbox`, the non-login user sandboxes run as. The Dockerfile is multi-stage. The first stage builds the `safeclaw` binary from the Go source; the second is the runtime image. The Dockerfile, `setup/`, and the Go source are embedded in the binary, so `safeclaw build` works from any directory. Tagged releases also publish a multi-arch image to `ghcr.io/josegonzalez/safeclaw`, which `safeclaw pull` fetches and tags locally as `safeclaw`, along with the built-in [variants](#image-variants), built on top of it.

Build inputs are pinned: the `golang` and `ubuntu` base images by digest (kept current by Dependabot), the Claude Code, Node.js, and yt-dlp versions by `ARG`, and claude-code-tips by commit SHA (`CLAUDE_CODE_TIPS_COMMIT`) rather than by tag, so a moved tag can't change the build. The status line script is fetched from the same claude-code-tips commit as the DX plugin, the build checks that the plugin marketplace is checked out at that commit, that dx's source in it is that same checkout (`./`), and that the installed plugin records the commit, and the status line script and yt-dlp are checked against pinned SHA-256s. The Claude Code binary is fetched for its version directly rather than through `claude.ai/install.sh`, and checked against a pinned SHA-256 per architecture, taken from that version's signed `manifest.json`, both before it runs and once it has installed itself. The nodesource and GitHub CLI apt keyrings are committed in `setup/apt` rather than fetched, and the build checks their primary key fingerprints against recorded ones. Playwright MCP, node-lief, and yarn, with every transitive dependency, are installed with `npm ci` and no install scripts from the lockfile in `setup/npm`, which records each package's integrity hash, into `/opt/safeclaw/npm`, and their commands are linked into `/usr/local/bin`. Each Playwright browser archive is checked against its SHA-256 in `setup/playwright/archives.sha256` before it is unzipped, and an archive with no line there fails the build.

Claude Code's own config is root-owned and read-only, so the agent can't rewrite its settings, status line, skills, or instructions for the life of the container: `~/.claude/settings.json`, `~/.claude/CLAUDE.md`, `~/.claude/scripts/`, and `~/.claude/skills/`. An empty `~/.claude/settings.local.json`, `~/.claude/AGENTS.md`, and empty `~/.claude/agents/`, `commands/`, `output-styles/`, `rules/`, `workflows/` and `routines/` are created the same way, so the agent can't add them to override the settings or add its own instructions, agents and commands. The plugins in `~/.claude/plugins`, whose hooks and skills Claude Code runs, are root-owned too. `/home/sclaw` and `~/.claude` are owned by root with group `sclaw` and mode 1770, so sclaw can still create and change its own files there (history, `.claude.json`, cloned repos) but the sticky bit stops it from deleting or renaming the root-owned files, or `~/.claude` itself, to replace them.

The Claude Code install is root-owned as well: `~/.local/bin`, which is early in `PATH`, and the binary in `~/.local/share/claude`. Claude Code's auto-updater is disabled, so it never writes to its install. `~/.local` and `~/.local/share` are root:sclaw 1770 like the home folder, so other tools can still keep data there, but nothing can be added to `~/.local/bin` to shadow `claude`, `node` or the other commands Claude Code runs. The shell's startup files are root-owned: `~/.bashrc`, `~/.profile`, `~/.bash_logout`, and a `~/.bash_profile` that only sources `~/.profile`, which is there so the agent can't add one that login shells would read instead. `~/bin`, which `~/.profile` adds to `PATH`, is an empty root-owned folder.

The home folder is Claude Code's working directory, so it is also the project folder. Empty, root-owned `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `AGENTS.override.md` there keep the agent from adding project instructions. The project's `.claude/` is `~/.claude` itself.

The only MCP server, Playwright, is defined in Claude Code's managed MCP config at `/etc/claude-code/managed-mcp.json` (from `setup/managed-mcp.json`), with the full path to `playwright-mcp`. A managed MCP config takes exclusive control of the server list: `claude mcp add` is refused, and servers written into `~/.claude.json` or a `.mcp.json` are ignored, even with `CLAUDE_CONFIG_DIR` pointed elsewhere. An allowlist of server commands in `settings.json` would not be enough, since Claude Code still reads each server's `env` from `~/.claude.json`. Having a managed config has two side effects. Claude Code turns on its built-in `cc-plugin-sec-default` plugin, which keeps managed hooks, prompt content, settings and tool policy out of reach of the plugins a person installs. It also leaves out its built-in Artifacts MCP server. `~/.claude.json` itself stays owned by sclaw, since Claude Code rewrites it on every start (by writing a temp file and renaming it over the old one), and with the MCP servers moved out it only holds Claude Code's own state.

The env file every bash sources and git's config are root-owned too; see [how env vars are passed](#how-env-vars-are-passed) and [GitHub CLI](#github-cli). Auto memory in `~/.claude/projects` is meant to persist, and is mounted from the host, unless the session [turns it off](#auto-memory). `/ms-playwright`, where Chromium lives, and `/opt/safeclaw/npm`, where Playwright MCP lives, are root-owned and read-only for everyone else, so the agent can't replace the browser or server the managed MCP config launches. Chromium runs with `--no-sandbox` because its sandbox can't work in a session: it needs either unprivileged user namespaces, which docker's seccomp profile refuses to a container without `CAP_SYS_ADMIN` (a session has no capabilities at all), or a setuid helper, which `no-new-privileges` disables. The container is the boundary instead.
