# Dashboard

`safeclaw dashboard` serves the dashboard on `127.0.0.1:7680` (`--port` to change) and prints a URL carrying a random token, such as `http://127.0.0.1:7680/?token=...`. Opening it logs the browser in with a cookie and a second secret, which the page keeps in `localStorage` and sends in a header. Every route but `/dashboard-proof`, static files included, returns 401 without the cookie, and every route but the page shells and static files also needs the secret. A login lasts 7 days at most, and ends after 12 hours with no tab open; the `log out` button in the header ends it at once. See [dashboard access](architecture.md#dashboard-access) and [logins and logout](architecture.md#logins-and-logout).

## How it works

Pages and fragments are rendered on the server with `html/template`. [htmx 4](https://htmx.org) handles requests and swaps, and its SSE extension handles live updates. htmx and the extension are vendored in `internal/dashboard/static` and embedded in the binary, as are [xterm.js](https://xtermjs.org) 5.5.0 and its fit addon 0.10.0 in `static/xterm`. `internal/dashboard/VENDOR.md` records where each vendored file came from and its SHA-256, which a test checks; see [updating vendored front-end files](development.md#updating-vendored-front-end-files). The only hand-written JavaScript is `static/app.js`, which keeps the login's secret and adds it to every request, clears the page on logout, opens and closes the `<dialog>` modals, copies the attach command to the clipboard, refreshes an iframe, normalizes the session name as you type, and runs the session terminal client.

## Session terminals

Each running session's frame is an iframe of `/sessions/NAME/terminal`, the dashboard's own terminal page, and the table's URL and the frame's `open` link open the same page in a new tab. The page runs xterm.js and speaks ttyd's protocol over `/sessions/NAME/terminal/ws`, which the dashboard proxies to the session's ttyd, adding the session's credential. The browser never loads anything from the session's port, so the dashboard works the same whatever the session serves there. The iframe's `sandbox` attribute allows scripts, its own origin (for the cookie and the WebSocket), and popups that escape the sandbox (for links, which open in a new tab). That doesn't isolate the terminal page from the dashboard: with both scripts and its own origin, the framed page is same-origin with the dashboard, and its script could reach the dashboard's page or lift the sandbox. What keeps the session out is that the terminal page only runs the dashboard's own scripts, which its `Content-Security-Policy` enforces (`script-src 'self'`, no inline script), and that the session only sends terminal bytes over the WebSocket, which xterm.js renders as text. Terminal links open in a new tab only when they are http or https URLs whose host isn't `localhost`, a name under `.localhost`, or a loopback or unspecified address, on any port, since the dashboard's cookie is sent to its host on every port and session terminals listen on loopback too. This is the policy `safeclaw attach` applies to the links it passes on. See [dashboard access](architecture.md#dashboard-access) and [terminal credential](architecture.md#terminal-credential).

A frame appears as soon as its session's container starts, which is before the session's ttyd credential is written and ttyd listens. Until then the proxy accepts the WebSocket and closes it with code 1013 (try again later), since a browser can't see the status of a refused upgrade. The page shows `[starting...]` and tries again with a new ticket, waiting 250 milliseconds and twice as long each time up to 2 seconds, for up to a minute, then says the terminal did not start. Any other close shows `[disconnected: click refresh to reconnect]`.

## Live updates

The server runs one `docker events` stream of container and network events. When it exits it is restarted after a second, and the wait doubles each time it exits again, up to 30 seconds, until a stream lasts that long. Whenever a `safeclaw-*` container is created, started, stopped, dies, or is destroyed, or one is connected to or disconnected from a network (checked by container ID, since network events name the network), it sends a `sessions` event to every browser on `/events`. The container behind a network event is inspected in the background, at most four at a time, so a slow inspect doesn't hold up other events. Events may be missed while the stream restarts, and an event line over 1 MiB or that isn't JSON is skipped, so both also send a `sessions` event, and `refresh` on `/api/events`. The page then re-fetches the sessions table and the frames grid and morphs them into place (`innerMorph`/`outerMorph`). Unchanged iframes keep their DOM node, so running terminals don't reconnect when another session changes.

Sandboxes are listed in the table with a `sandbox` badge and only their stop or delete button. They have no URL, info dialog, start button, or iframe, and start and info return 409 for them. Create refuses a sandbox's name like any other taken name. One-off sandboxes also get a `one-off` badge, and stopping one removes its row, because docker removes the container when it stops.

The new session dialog has an image variant picker listing `base` and every [variant](architecture.md#image-variants). Its first option, `default`, sends no variant, so the session gets the configured default, named in the option. Sessions and sandboxes on a variant show a badge with its name. Variants are read from the config file on every page load; if the file is invalid, the picker shows only `default` along with the error.

The dialog also has a secrets picker: `all secrets` (the default), `no secrets`, or `only checked` with a checkbox per stored secret. The checkboxes are only shown, with CSS `:has()`, while `only checked` is picked. Sessions that don't receive every secret show a `no secrets` or `N secrets` badge, with the names in its tooltip. Sandboxes never get one, since they never receive secrets. See [choosing secrets](architecture.md#choosing-secrets).

Interactive sessions have an `offline` or `online` button next to stop or delete, and in the frame bar. `offline` takes the session offline with the unnamed hold. `online` releases the unnamed hold; if other owners still hold the session, it opens a dialog listing them and their reasons, with a field for the session's name. Its `force online` button, which releases every hold, is enabled only once the name is typed, and the server refuses a force whose typed name doesn't match. Offline sessions show an `offline` badge with their holders and reasons in its tooltip, `offline` in place of their URL, and a placeholder in place of the iframe, which comes back when they reconnect. See [offline sessions](architecture.md#offline-sessions).

A banner above the table says when no Claude Code token is stored, or when it has expired or expires within 30 days, and names `safeclaw auth login`. It re-fetches with the table on every `sessions` event. Storing a token fires no docker event, so the banner clears on the next session change or page load. See [Claude Code](architecture.md#claude-code).

Dashboard actions respond with `HX-Trigger: sessions`, so the page also refreshes right away without waiting for the docker event.

## Two-click confirm

Stop and delete need two clicks, and make the checks the CLI's `stop` and `rm` make: the name must be valid, and the container must exist and be a session or a sandbox. Unlike the CLI, both types are accepted, since the table lists both. The first POST returns a "stop?"/"delete?" button that posts with `confirm=1`. That button also contains an element that fetches the normal button again after 3 seconds, which reverts it if you don't confirm.

## Routes

| Route | Purpose |
|-------|---------|
| `GET /` | Page shell, with no state. It loads every fragment below with htmx |
| `GET /fragments/sessions`, `GET /fragments/frames` | Table (or empty state) and frames grid |
| `GET /fragments/auth` | Claude Code token banner, empty while the token is valid |
| `GET /fragments/options` | The new session form's variant and secrets pickers |
| `GET /events` | SSE stream of `sessions` events |
| `POST /sessions` | Create a session (`name`, `volume`, `variant`, `secrets` as `all`, `none`, or `only` with a `secret` field per name, `query`, `open_tab`). Errors return 422 and render in the dialog |
| `GET /sessions/validate?name=` | Name hint shown while typing |
| `GET /sessions/{name}/info` | Session info dialog with the `safeclaw attach` command |
| `GET /sessions/{name}/actions` | Normal action button, used to revert a confirm |
| `GET /sessions/{name}/terminal` | The session's terminal page |
| `GET /sessions/{name}/terminal/ws?ticket=` | WebSocket (subprotocol `tty`) proxied to the session's ttyd with its credential. Takes the cookie with a ticket from `/tickets` in place of the secret. Only the dashboard's own `Origin` is accepted; 404 for a session without a running, online terminal, 502 when the lookup fails otherwise. A session whose terminal is still starting (no ttyd credential yet, or ttyd not answering) gets the upgrade and then a close with code 1013 |
| `POST /tickets` | `path` is a terminal WebSocket path. Answers with a ticket that opens it once within 30 seconds, only with the cookie of the login that asked for it, 400 for any other path, 503 while 64 are outstanding |
| `POST /logout` | Ends the browser's login, so its cookie, secret, and tickets stop working and its streams and terminals close. 204 with `HX-Trigger: logged-out` and a cookie that clears it, 400 for the bearer token |
| `POST /sessions/{name}/start`, `/stop`, `/delete` | Session actions |
| `GET /dashboard-proof?nonce=` | Needs no login. 204 with the proof that this dashboard holds its token in the `Safeclaw-Proof` header, 400 for a nonce that isn't 16 to 128 letters, digits, `-` or `_`. See [finding the dashboard](#finding-the-dashboard) |
| `POST /sessions/{name}/offline`, `/online` | Take a session offline with the unnamed hold, or release it. When other holds remain, `/online` answers with the force dialog, retargeted to the info dialog. `force=1` releases every hold, and needs `confirm_name` set to the session's name (422 otherwise) |

The JSON API from upstream is kept for scripting. Send the token from `~/.config/safeclaw/dashboard/PORT.token` as a bearer token:

```bash
curl -H "Authorization: Bearer $(cat ~/.config/safeclaw/dashboard/7680.token)" http://127.0.0.1:7680/api/sessions
```


| Route | Body | Response |
|-------|------|----------|
| `GET /api/sessions` | | `[{name, port, url, volume, active, type, variant, autoRemove, secrets}]`, `type` is `session` or `sandbox`, `variant` is the image variant (`""` for the base image), `autoRemove` is true for one-off sandboxes, `secrets` is `null` for every secret or the list of names the session receives (`[]` for none), `network` is `online`, `offline`, `none`, `host`, or `shared`, and `holds` lists `{owner, reason, since}` for each hold keeping it offline (`owner` is `""` for the unnamed hold) |
| `POST /api/start` | `{"name"}` | `{success, url}`, or 409 for a sandbox or for an offline session still published on `127.0.0.1`, which starting would recreate on `[::1]`. `url` carries the session's ttyd credential, like the URL `safeclaw run` prints |
| `POST /api/stop` | `{"name"}` | `{success}`, or `{success: false, error}` with 400 for an invalid name, 404 for a missing session, or 409 for a container that is neither a session nor a sandbox |
| `POST /api/delete` | `{"name"}` | As for stop |
| `POST /api/net/off` | `{"name", "owner", "reason"}` | `{success, offline, holds}`, or 409 for a sandbox or a network that can't be disconnected |
| `POST /api/net/on` | `{"name", "owner", "force"}` | `{success, offline, holds}`. `offline` stays true while other holds remain. 409 with the holders when `owner` holds nothing but others do |
| `POST /api/create` | `{"name", "volume", "variant", "secrets", "query", "recreate"}` | `{success, url}` (with the credential, as for start) or `{success: false, error}`, with 400 for an invalid name, 409 for a sandbox name, for an existing session's name unless `recreate` is true, or when it would recreate an offline session. With `recreate`, an existing session is started, and recreated when a volume is given or the variant or secrets differ, as `safeclaw run` does. `secrets` is `"all"`, `"none"`, or a list of names; leaving it out keeps an existing session's set, or gives a new one every secret |
| `GET /api/events` | | SSE, `data: <docker action>`, or `data: refresh` when events may have been missed |

## Security

Every request must use a `Host` the dashboard advertises (`127.0.0.1`, from the printed URL, or `localhost`, which is redirected to `127.0.0.1` before a browser gets the cookie), which blocks DNS rebinding. The dashboard listens on both `127.0.0.1` and `[::1]`, so no other local user can take the `[::1]` side of `localhost:PORT` and receive a token sent there, and it doesn't start when something else holds either one. On a host without IPv6 loopback it warns and listens on `127.0.0.1` only. A `Host` of `::1` is refused, since the cookie is only set for `127.0.0.1`. Requests must also carry the `safeclaw_dashboard_PORT` cookie or the launch token in an `Authorization: Bearer` header, which keeps out code in session containers and other local processes. A `GET` with the token in its `token` query parameter sets the cookie and redirects to the same URL without it, with the login's secret in the fragment. The cookie's value is not the token but a separate random value the dashboard keeps in memory, and the token isn't accepted as the cookie. Cookies aren't scoped by port, so the browser also sends the cookie to anything else listening on `127.0.0.1`, such as a session created before sessions moved to `[::1]` or another local app, which can replay it with any headers. So the cookie alone opens only the page shells and static files, which show no state; everything else needs the secret in the `Safeclaw-Secret` header too, or a ticket for the terminal WebSocket. The secret lives in the dashboard origin's `localStorage`, which no other port can read, and no route returns it. It stays in the browser profile after the dashboard exits but is worthless then. See [the second secret](architecture.md#the-second-secret). Starting such a session with `safeclaw run` or the dashboard recreates it on `[::1]` so nothing a session controls receives it, once its image's ttyd accepts `[::1]` URLs; until then `run` warns that the image needs updating. State-changing requests also go through Go's `http.CrossOriginProtection`, so other websites can't drive the dashboard from your browser. The auth check is `Access.Middleware` in `internal/dashboard/access.go`, so routes added later get it by being on the same handler. The terminal WebSocket proxy is behind it too, and never forwards the browser's cookie or `Authorization` header to a session.

### Finding the dashboard

`safeclaw run` and `safeclaw url NAME --open` open a running dashboard's terminal page instead of the URL with the session's credential. They find dashboards by their token files, the default port first, and the listener on each file's port must prove it is the dashboard holding that file's token before it is chosen. The CLI sends `GET /dashboard-proof` a random nonce and nothing else, with no token, cookie, or proxy, and the dashboard answers with HMAC-SHA256, keyed by its token, of its port and the nonce, base64url-encoded in the `Safeclaw-Proof` header. The CLI checks it in constant time. Something else listening on the port of a file left by a dashboard that has exited, such as another local user who took over the freed port, can't compute the proof, so the browser is never sent to it and the stale token is never disclosed. A dashboard on another port can't answer for this one either, since the port is part of what is signed. Answering anyone's nonce gives nothing away: the proof can't be turned back into the token, and nothing accepts a proof in place of it. A file whose port refuses the connection or answers without a valid proof is removed, but only while it still holds the token that failed, so a dashboard that started on the same port meanwhile keeps its file. A port that doesn't answer within a second is skipped and its file kept. The dashboard removes its token file when it stops on SIGINT, SIGTERM, or SIGHUP, so closing the terminal it runs in leaves no stale file. A dashboard started under `nohup`, with SIGHUP ignored, keeps ignoring it, so it keeps running, and keeps its token file, when that terminal closes. A crash or SIGKILL still can, and the proof keeps such a file from being trusted.

Every response, 401 and 403 refusals and static files included, carries `X-Frame-Options: DENY` and a `Content-Security-Policy` with `frame-ancestors 'none'`, so no other page can frame the dashboard and overlay it to pass clicks through. `http.CrossOriginProtection` can't catch that, because a framed dashboard's own requests are same-origin, and another loopback port gets the `SameSite` cookie. The one exception is the terminal page, which the frames grid iframes: it gets `X-Frame-Options: SAMEORIGIN` and its own policy, which has `frame-ancestors 'self'`, in place of the default rather than alongside it, since a browser enforces every policy it gets. So only pages on the dashboard's own origin can frame it. The headers are set by `refuseFraming` in `internal/dashboard/server.go`, which wraps every other check.

The default policy, `pageCSP` in the same file, also has `default-src 'self'`, `script-src 'self'` and `style-src 'self'`, with no inline script or style and no eval, plus `object-src 'none'` and `base-uri 'none'`, so markup that reached a page some other way couldn't run script. The page keeps all of its script in static files, its htmx config is a `<meta>` tag, which isn't script, and htmx's `hx-on` attributes, which htmx runs with `Function` and the policy refuses, aren't used. A test fails on any inline script, event handler, style attribute, or `hx-on` in the templates. htmx's indicator styles are a constructed stylesheet, which the policy doesn't cover, and the only `data:` source allowed is the empty favicon.

Templates build URLs with `path` and `revert`, which path-escape the session name, and `hx-vals` with `vals`, which marshals the JSON, so a quote in a value can't add a key once the attribute is decoded. The action buttons' style (`variant`, `link` for the frame bar) is echoed from requests, so anything but `link` is rendered as the table style.
